# Palantir 数据表绑定、修改落地与冲突处理调研

> 本文基于对 Palantir Foundry 官方文档(zh 机器翻译版)的实际抓取核实,以及 ChunJun(FlinkX 现名)master 分支源码/文档/示例的核实整理。
> 目的:厘清 Palantir 如何绑定数据、修改如何落地、冲突如何解决,并对照我方(直连业务库 + 治理中心 ETL)架构,给出可落地的方案。
> 抓取来源:`docs/datasource/py/palantir_docs/*.txt`(virtual-tables / edits-how-applied / action-webhooks 等);ChunJun 源码 `github.com/DTStack/chunjun` master。

## 一、Palantir 的数据绑定:两种方式

数据进入 Foundry 本体有两条路,写方向都**不回写源表**,区别在读:

| 方式 | 数据在哪 | 是否落库 | 特点 |
|---|---|---|---|
| **同步到数据集(Dataset)** | 拷进 Foundry 自己的存储 | 是(副本) | 有版本/分支/全功能,性能好,但重复存储 |
| **虚拟表(Virtual Table)** | 留在源系统,Foundry 只存指针 | 否(下推查询) | 省存储、实时、不搬数据;但**只读**,不支持版本/分支/部分功能 |

关键概念澄清:

- **原始物理表**:源系统里的表(Oracle/MySQL/SAP…),是你自己的。
- **Foundry 数据集**:Foundry 在自己存储里维护的一份数据实体(底层是对象存储上的 Parquet 等文件),**是 Foundry 自己的一份数据**,不是原表也不是指针。内容可能来自同步、管道计算或编辑合并。
- **虚拟表**:指向源系统的指针,**不是数据集**,故意不落库,以换取省存储/实时/下推。

虚拟表当前 GA 支持的源:Amazon S3、Azure ADLS Gen2、BigQuery、Snowflake。虚拟表**只能作为输入**;一旦要在其支撑的对象上做操作(Action),必须先"物化"成数据集(落进对象存储)才能写。

## 二、修改如何落地:编辑层,而非原表

### Action / Decision 都不写原表

- **Action(操作)**:可作用于单个对象、单个链接实例,或一个对象集(即**可批可单**)。改动**立即写入对象数据库的实时索引**,再由 Funnel 服务定期物化落盘。
- **Decision(决策)**:粒度是**单个对象实例一条**,记录"为什么这么改"的判断,作为独立可追溯的原语。
- 二者**都不会修改源表,也不会回写源系统**。

### 三层存储模型

| 层 | 谁写 | 内容 |
|---|---|---|
| 输入数据源(物理表/虚拟表) | 数据管道 / 源系统 | 原始数据,只读 |
| 对象数据库实时索引(OSv2/Phonograph) | Action/Decision 实时写 | 对象当前状态(临时) |
| Funnel 合并数据集(用户编辑层) | 定期物化落盘 | 源数据 ∪ 用户编辑,持久化 |

"合并数据集" = **源数据集与用户编辑分开存、读时(实际是写入/索引时前置)合并出的结果**;原表始终不动。

### 物化触发时机

- 源数据集出现**新事务(transaction)**时,或
- 无新数据但检测到编辑时,最多每 6 小时一次。

### 回写源系统的唯一途径:Webhook

- Webhook 可向外部系统(Salesforce/SAP/任意 HTTP)发请求修改其数据。
- 分**数据输出**(对象更改前执行,失败则不改本体,向用户显示失败)与**副作用**(对象更改后执行,可批量,失败不显示)。
- **只有"部分事务性"**:可能外部成功但本体失败,或反之。

## 三、冲突如何解决:分层优先级,而非时间先后

同一对象既被数据源刷新、又被用户编辑,靠**冲突解决策略**在合并时决定取值:

### 策略 1:应用用户编辑(默认)

- 对象最终状态**始终由用户编辑决定,无论数据源未来如何更新**。
- ETL 再同步,只写进"源数据集"那一份;合并时被编辑层压住,**盖不掉**。
- **粒度是字段级**:被编辑的字段取编辑值,未编辑字段取源最新值。

### 策略 2:应用最新值(可选)

- 用户编辑仅当其时间戳**晚于**数据源时间戳时才应用;否则忽略。
- 此时"同步晚就覆盖"才成立——但这是主动选择的策略,非默认。
- 要求数据源含 UTC 时间戳属性(date 类型无效)。
- "仅编辑属性"无论时间戳如何,编辑总应用。

### 为什么不怕"落库早晚 / 时序竞态"

- 编辑与源数据**分开持久存储**,谁都不覆盖谁的物理存储。
- 合并**反复发生**:源来新事务就再合一次,晚到的数据下次合并自然算进去,只是"稍晚生效",不会丢。
- 是靠**分层优先级**规避覆盖,不是靠时间先后。

### 如何做到"不扫全量"

- **源侧**:靠数据集"新事务事件"通知,事务只含增量行。
- **编辑侧**:靠 Funnel 队列的**偏移量(offset)**书签,只读上次之后的新编辑。
- 两条增量流在**主键**上对齐,只合并受影响的行。

### 命门:主键

- 冲突判定 = **主键定位到行 + 逐字段判优先**。
- 没有稳定唯一主键,两份无法对齐,整套机制不成立。
- Palantir 要求入本体前必须有稳定唯一主键(可在管道里造)。

## 四、我方架构对照

### 我方现状:直连业务库 CRUD

- 直接读写**原始物理表**,单一写入来源(应用直接改),**不存在 ETL 回刷冲突**。
- 有**执行记录**:变化前值 + 变化后值 + 修改/删除 SQL → 可追溯、可回滚、可审计。

### 与 Palantir 的本质区别

| | 我方(直连改表) | Palantir 编辑层 |
|---|---|---|
| 数据来源 | 单一:应用直接写原表 | 双重:源管道 + 人工编辑 |
| 改动落在哪 | 直接写原表 | 独立编辑层,源表不动 |
| 执行记录角色 | 旁路(记录既成事实) | 编辑层本身参与读取 |
| 要不要仲裁层 | **不需要**(单来源) | 需要(仲裁两来源) |

结论:**编辑层/冲突解决那套是为"多写入来源"准备的**。我方单来源直改,那套对我方是过度设计;执行记录做审计+回滚已足够。

### 概念纠正

- 我方执行记录 ≠ 虚拟表物化。前者是"改动的前后流水(增量)",后者是"完整当前数据副本(全量)"。
- 我方对应"数据本身"的是**原始物理表**,没有、也不需要"物化副本"这一层。

## 五、若引入"集成数据 + Action + Webhook 回写"的落地方案

前提场景:数据先集成到治理中心(一份副本),Action 改副本,再 Webhook 推回源。此时产生**两个写入来源**(周期增量 ETL + 用户 Action),冲突问题回归。

### 核心思路(我方设计)

1. **执行记录当变更事件源**驱动 Webhook(异步、可重试、可补偿)。
2. **冲突用可重放 Action 兜底**:ETL 覆盖了人工改动就重放 Action 改回,以"幂等重放"代替"冲突锁"。

### 必须拧紧的螺丝

- **① 执行记录加 Webhook 推送状态**:`PENDING / SENT / FAILED`,失败才能挑出重推。
- **② 重放必须幂等 + 三值判断**:
  - 当前值 = after → 已达目标态,跳过(勿重复推 Webhook);
  - 当前值 = before(被 ETL 刷回) → 重放改回 after;
  - 当前值 = 第三值(他人又改) → **真冲突,告警人工决定,勿闷头覆盖**。
- **③ 重放触发时机**:挂在 **ETL 增量任务之后主动对账**最稳。

### Webhook 非事务性带来的失败模式(结合周期增量)

| 情况 | 结果 |
|---|---|
| Action 改副本 ✔ + Webhook 回源 ✔ | 下次 ETL 刷回同值,一致 ✅ |
| Action 改副本 ✔ + Webhook 失败 ✘ | 副本新值、源旧值 → 下次 ETL 增量把副本刷回旧值,**人工改动悄悄丢失** ❌ |

→ 必须决定 ETL 与人工编辑谁优先,否则失败的 Webhook 会被下一轮增量抹掉。

## 六、普通治理 ETL(无事务事件/无偏移量)约束下的方案

若 ETL 是黑盒批同步(不告诉你"改了哪些主键"),Palantir 的"增量驱动自动收敛"做不了。破局点:**不追踪"ETL 改了什么"(没这能力),而是盯住"你自己改过什么"(天然有此清单)**。

| 处境 | 方案 |
|---|---|
| 能改 ETL 写入逻辑 | **A(最优)**:给人工编辑的行/字段打标记,ETL 写入时 `WHERE NOT manual_edited` 跳过 → 从源头无冲突,无需对账 |
| 不能改 ETL,但可维护登记表 | **B**:人工编辑进"登记表(主键+字段+目标值+状态)";ETL 跑完只遍历**登记表**(小)比对当前值,被覆盖则重放+Webhook |
| 表很小、改动很少 | C:全表对比(大表会死,不推荐) |

对账范围是"人工编辑登记表",不是目标全表。

## 七、用 Kafka 升级为事件驱动(补齐缺失的变更事件流)

若集成/ETL 输出可挂 Kafka,则补齐了"变更事件流",等价于 Palantir 的"数据集事务事件"。

### 架构

```
ETL 输出 ──→ Kafka(source-changes topic,每条带主键+变更值+op)
                        │
              冲突消费者(consumer)
                        │
          事件主键 ∩ 人工编辑登记表(O(1) 点名,不扫全表)
                        │
        ┌───────────────┼───────────────┐
   命中人工编辑        未命中          第三值
   → 按策略仲裁      → 放行           → 告警
```

- 人工编辑也发 Kafka(edit-events topic),Webhook 消费者订阅,**offset 天然当游标**,失败进 DLQ,替代自维护 PENDING/SENT。

### 三颗必须拧紧的螺丝

- **① 主键做分区 key**:Kafka 仅保证分区内有序,同主键变更必须进同一分区,否则旧值后到覆盖新值。
- **② 幂等消费**:Kafka 至少一次投递,消费端按"主键+版本/时间戳"去重或比当前值。
- **③ 主键+字段级仲裁**:仍需自己实现取源/取编辑的判定;**无主键的表 Kafka 也救不了**。

## 八、ChunJun(FlinkX)Kafka 输出能力核实

已核实 ChunJun master 源码/文档/示例,**支持本方案所需的 Kafka 输出**:

| 能力 | 支持情况 | 依据 |
|---|---|---|
| Kafka Sink | ✅ `kafkasink/kafkawriter`;SQL 侧 `kafka-x`/`upsert-kafka-x` | `kafka-sink.md` |
| **主键分区保序** | ✅ `partitionStrategy:"hash-by-key"` | `PartitionStrategy.java` 枚举(all-to-zero / hash-by-key);示例 `binlog_kafka_partition_by_key.json` |
| **变更类型 op + before/after** | ✅ CDC + debezium-json | sink 文档示例输出 `{"before":...,"after":...,"op":"c/u/d"}` |
| 指定 record key | ✅ `key.fields` + `key.format` | sink 文档 |
| 一致性语义 | `sink.semantic`:at-least-once(默认)/exactly-once/none | sink 文档 |

### 关键:MySQL "增量读取"的两条路,意义完全不同

| | `polling` 轮询增量 | `binlogreader` CDC |
|---|---|---|
| 原理 | 定时 `SELECT WHERE 增量列 > 位点` | 读 binlog |
| 删除 | ❌ 抓不到 | ✅ |
| 旧值(before) | ❌ 只有当前行 | ✅ |
| op(增/改/删) | ❌ 无 | ✅ `op:c/u/d` |
| 前置条件 | 表需单调递增列 | 需开 binlog(row 模式)+ 权限 |
| 配置 | `polling:true`+`increColumn`+`startLocation`+`pollingInterval` | `binlogreader`+`cat:"insert,delete,update"` |

结论:

- **polling 增量 = 普通批 ETL 层次**,只发"当前数据行",无 op/before/after → **撑不起事件驱动方案**,只能退回登记表比对(方案 B)。
- **只有 binlog CDC** 才产出完整变更流,配 `hash-by-key` 分区发 Kafka,事件驱动+Webhook 方案**才真正成立**。
- **最后一道门槛:MySQL 能否开启 binlog(row 模式)。** 能开走 CDC;不能开只能降级。

### binlog → Kafka 参考配置(仓库示例结构)

```json
"reader": {
  "name": "binlogreader",
  "parameter": {
    "jdbcUrl": "jdbc:mysql://host:3306/db",
    "cat": "insert,delete,update",
    "pavingData": true,
    "splitUpdate": true
  }
},
"writer": {
  "name": "kafkawriter",
  "parameter": {
    "partitionStrategy": "hash-by-key",
    "topic": "your-topic"
  }
}
```

## 九、总体结论

1. Palantir 的编辑层/物化/冲突解决,本质是为"源数据在别处、不能直接写源、多写入来源"这一先天约束设计。
2. 我方直连业务库、单一写入来源,不具备该约束,那套多为过度设计;现有执行记录做审计/回滚已足够。
3. 若未来走"治理中心副本 + Action + Webhook 回写",则回归多来源冲突,需按第五~七节补齐:执行记录带状态、重放幂等+三值判断、ETL 后对账;有条件上 Kafka 事件驱动。
4. ChunJun 能力齐备,但**成败取决于能否用 binlog CDC**;polling 增量不足以支撑事件驱动。
5. 主键是所有方案的地基:无稳定唯一主键,Palantir 合并、我方重放对账、Webhook 回写全部无法安全完成。
