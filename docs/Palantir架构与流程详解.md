# Palantir 架构与流程详解

> 面向团队理解 Palantir(Foundry / AIP / Gotham / Apollo)的架构设计与数据流。
>
> **说明**:Palantir 未完全开源,本文基于其公开文档(docs.palantir.com)、工程博客、公开演讲整理。涉及内部实现细节处标注为"设计理念/推断",不做确证性断言。术语以 Palantir 官方叫法为准,括号内给出对照解释。

---

## 1. 产品全景

Palantir 不是单一产品,而是一组围绕"数据到决策"的平台:

| 产品 | 定位 | 目标客户 |
|---|---|---|
| **Foundry** | 商业数据平台:数据集成 + 本体 + 分析 + 应用 | 企业(制造、医疗、金融、能源) |
| **Gotham** | 情报/国防分析平台(起家产品) | 政府、军方、情报机构 |
| **AIP** (Artificial Intelligence Platform) | 把 LLM 接入 Foundry 本体与工作流 | 上述全部,AI 化升级 |
| **Apollo** | 持续部署/运维基础设施(把上述产品交付到各种环境) | 内部 + 客户私有化环境 |

**核心主线**:Foundry 是数据底座,Ontology(本体)是灵魂,AIP 是 2023 后的 AI 层,Apollo 是把这一切部署出去的引擎。下文以 **Foundry + Ontology** 为主。

---

## 2. Foundry 分层架构

自底向上五层:

```
┌─────────────────────────────────────────────────────────┐
│  ⑤ 应用层     Workshop(低代码应用)/ Quiver / Slate      │
│               Contour(可视化分析)/ 报表 / 运营应用        │
├─────────────────────────────────────────────────────────┤
│  ④ AIP 层     LLM 编排 / Agent / AIP Logic / 语义搜索     │
├─────────────────────────────────────────────────────────┤
│  ③ 本体层     Ontology:Objects + Links + Actions         │
│               ★平台灵魂:业务语义层,连接数据与应用         │
├─────────────────────────────────────────────────────────┤
│  ② 转换层     Pipeline Builder / Code Repositories        │
│               Spark 批处理 / Flink 流处理 / 数据血缘        │
├─────────────────────────────────────────────────────────┤
│  ① 集成层     Data Connection(数百种连接器)              │
│               数据集(Dataset,Parquet on 对象存储)        │
└─────────────────────────────────────────────────────────┘
        贯穿全层:Lineage(血缘)/ Versioning(版本)/ Security(权限)
```

三条"贯穿维度"(每一层都带):**血缘、版本、权限**。这是 Foundry 区别于普通数据平台的关键——不是事后附加,而是每一层原生携带。

---

## 3. 集成层(①):数据进来

### 3.1 Data Connection
- 数百种连接器:数据库(JDBC)、消息队列(Kafka)、对象存储(S3/HDFS)、SaaS API、文件、流。
- 支持**批量**和**流式**两种摄取。
- 连接器运行在 **Agent**(部署在客户网络内的轻量代理)里,数据可以"不出客户网络"就被 Foundry 索引——这是私有化/合规场景的关键。

### 3.2 Dataset(数据集)
- 摄取进来的原始数据落为 **Dataset**,物理上是**对象存储上的 Parquet 文件**(列存)。
- **每个 Dataset 都是版本化的**:每次写入产生一个新的 transaction(事务/快照),旧版本保留 → 这就是"时间旅行"的物理基础(可查任意历史版本)。

---

## 4. 转换层(②):数据加工 + 血缘

### 4.1 两种加工方式
- **Pipeline Builder**:低代码可视化管道(拖拽式)。
- **Code Repositories**:代码化管道(PySpark / Java / SQL),走 Git 式版本管理、CI、代码评审。

底层执行引擎:**Spark(批)+ Flink(流)**。

### 4.2 血缘(Lineage)—— 护城河之一
- **每个 Dataset、每个转换步骤、甚至列级**,都自动记录"从哪来、经过什么转换、到哪去"。
- 形成一张全局 **DAG 血缘图**:点击任一数据点,可反查上游全部来源和处理步骤。
- **为什么关键**:审计、合规、"数据为什么错了"的根因定位、影响分析(改了上游哪些下游会受影响)——都靠它。这也是 Palantir 敢服务情报/国防的信任基础。

---

## 5. 本体层(③):平台的灵魂

**这一层是 Palantir 与所有普通数据平台的根本区别。** 前两层(集成、转换)很多公司都有,本体层是 Palantir 的核心资产。

### 5.1 Ontology 核心建模要素

理解 Palantir Ontology 时，可以先抓住 **Objects + Links + Actions** 三类核心能力；公开产品还包含 Interfaces、Functions、Rules 等配套概念，不能把“三要素”理解成完整且排他的元模型清单。

| 要素 | 含义 | 例子 | 对照数据库 |
|---|---|---|---|
| **Object Type**(对象类型) | 业务实体 | 客户、订单、飞机、供应商 | ≈ 表 |
| **Link Type**(关系类型) | 实体间关系 | 客户-下单-订单 | ≈ 外键,但是一等公民 |
| **Action Type**(动作类型) | **可对实体执行的操作** | "审批订单""调度飞机""标记预警" | **数据库没有对应物** |

**第三个 Action 是最容易被忽略、也最关键的**。它让本体从"只读的世界描述"变成"可写的操作面":
- Action 定义了**谁、在什么条件下、能对哪个对象做什么修改**。
- Action 执行时可以:改对象属性、创建/删除对象、触发外部系统调用、跑一段逻辑(AIP Logic)。
- Action 受**权限、规则和审计**治理；具体审批、自动化和跨动作编排由应用与运行时配置完成。

### 5.2 本体是"映射",不是"物化副本" ★核心设计

这是理解 Palantir 最关键的一点:

```
数据集(Dataset,物理数据)
      │
      │  Object Type 映射规则:
      │  "Customer 对象 ← customers 数据集,
      │   id 属性 ← cust_id 列,
      │   姓名 ← name 列"
      ▼
本体对象(逻辑视图,不额外存一份数据)
```

- 本体对象**不是数据的物理副本**,而是**指向数据集的一层语义映射**。
- Object Type 声明"我这个对象的数据来自哪个 Dataset 的哪些列",查询时按映射组装。
- **改映射立即生效**,不用搬数据;数据集更新,对象视图自动反映。
- 因为映射永远知道数据物理出处 → **血缘天然贯穿到本体层**。

**注意不是纯虚拟**:为性能,Foundry 会把本体对象**索引/物化到专门的存储**(Object Storage / 搜索索引 / 图索引),支撑快速检索和图遍历。所以是**"映射定义 + 按需物化索引"的混合**,不是每次都实时 join 源库。

### 5.3 实体对齐(Entity Resolution)在本体层
- 多源数据映射到同一 Object Type 时,"源A的张三"和"源B的张三"要合并成一个对象。
- 机制:**确定性匹配(唯一键)+ 概率匹配(相似度打分)+ 人在环确认 + 持续学习**。
- 合并规则是**本体层的配置**,不是焊死在管道里,想换策略改配置即可。

---

## 6. AIP 层(④):给本体接大脑

2023 年后 Palantir 的主打。核心思想:**LLM 不直接碰原始数据库,而是操作本体。**

### 6.1 为什么 LLM 要通过本体
- 裸表(`cust_id`, `amt`, `dt`)对 LLM 是"天书";本体对象(`客户.姓名`、`订单.金额`、带自然语言描述)是"业务语言"。
- 本体给 LLM 提供了:**语义标签**(每个对象/属性/关系是什么意思)+ **操作边界**(有哪些 Action 能做)+ **权限约束**(这个用户能看/能做什么)。

### 6.2 AIP 关键能力
- **AIP Logic**:可视化编排 LLM + 本体操作的逻辑(类似 tool-calling 工作流)。
- **LLM as Tool-caller**:LLM 通过调用**本体的 Objects/Links/Actions 作为工具**来读数据、做操作。它不会执行本体外的动作 → **schema/本体约束天然防幻觉、防越权**。
- **语义搜索**:对象上挂 embedding,支持自然语言模糊召回。
- **人在环 + 审计**:AI 提议的 Action 可以要求人工批准才执行,全程留痕。

---

## 7. Apollo(部署运维层)

- Foundry/Gotham/AIP 要交付到**极其多样的环境**:公有云、客户私有云、政府隔离网络、甚至断网环境。
- **Apollo** 是一套持续交付系统:声明式描述"什么版本该部署到哪个环境",自动编排升级、回滚、健康检查。
- 意义:让 Palantir 能在**无法直接访问客户环境**的情况下,持续安全地交付软件更新。是其 SaaS + 私有化双模式的支撑。

---

## 8. 贯穿全层的三大维度

### 8.1 血缘(Lineage)
已在第 4 节讲。要点:字段级、全局 DAG、自动生成、从源头贯穿到应用。

### 8.2 版本(Versioning / 时间旅行)
- Dataset 每次写入是新 transaction,旧快照保留。
- 可查询"某数据集在上周二的状态",可回滚。
- 管道也版本化(Code Repos 走 Git),可复现任意历史运行。

### 8.3 权限(Security)—— 细粒度 + 目的绑定
- **粒度**:不只到表,能到**行、列、单元格**。
- **Purpose-based access**:权限可绑定"使用目的"——同一份数据,为了目的A能用、为了目的B不能用(合规刚需,尤其政府/医疗)。
- **贯穿**:权限在集成层就打标,一路传递到本体和应用,查询/Action 执行时强制校验,全程审计。

## 9. 端到端数据流(一个完整例子)

以"某制造企业用 Foundry 做供应链风险预警"为例:

```
① 摄取
   ERP 订单库 / 供应商系统 / 物流 API / 新闻舆情
        │ Data Connection(连接器,数据可留在客户网络)
        ▼
   落为 Dataset(Parquet,版本化)

② 转换
   Pipeline Builder / PySpark 清洗、标准化、关联
        │ 自动记录字段级血缘
        ▼
   清洗后 Dataset

③ 本体映射
   定义 Object Type:供应商、零件、订单、风险事件
   定义 Link:供应商-供应-零件、零件-用于-订单
   定义 Action:"标记高风险供应商""触发备用采购"
   实体对齐:多源供应商合并成唯一对象
        │ (映射,不搬数据;按需物化索引)
        ▼
   活的业务本体

④ AIP 分析
   用户问:"哪些订单会因为 X 供应商断供受影响?"
   LLM → 调本体工具:遍历 供应商→零件→订单 关系
        → 定位受影响订单
        → 提议执行 Action"触发备用采购"(需人工批准)

⑤ 应用 + 行动
   Workshop 应用展示风险看板
   人工确认 → Action 执行 → 写回本体 + 调用采购系统 API
        │ 全程血缘 + 审计 + 权限校验
        ▼
   闭环:数据 → 洞察 → 决策 → 行动 → 数据
```

**关键**:第⑤步的"写回 + 触发外部系统"就是**行动闭环**——Palantir 的终极价值不在"看数据",而在"基于数据做操作并留痕"。

## 10. Palantir 架构的五个设计哲学

1. **本体是中心,不是数据库是中心**。所有应用、AI、分析都面向本体编程,不直接面向物理表。物理存储可换,本体稳定。
2. **映射优于搬运**。数据尽量留在原地,本体是语义映射层;物化只为性能,不为"拥有数据"。
3. **血缘/版本/权限是原生,不是插件**。每一层都携带,不可绕过。
4. **本体要能"动"**。Action 让本体从描述层升级为操作面,支撑行动闭环。
5. **AI 通过本体操作世界**。LLM 被本体的语义、边界、权限约束,天然防幻觉、防越权、可审计。
