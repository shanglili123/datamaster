# 审计血缘分析与改进方案(Palantir 对标 / Semantica 调研 / 现状差距 / 落地接线)

> 本文档回答三个问题:
> 1. **Palantir 的审计血缘到底强在哪**(对照 `docs/Palantir架构与流程详解.md`);
> 2. **Semantica(自称开源版 Palantir)怎么实现审计血缘**,与我们差距在哪;
> 3. **我们当前的实际状态**:集成(ETL)任务血缘没进 Neo4j、动作执行血缘没进 Neo4j、决策链不存在——以及把它们接线的**具体改进方案**。

## 1. Palantir 审计血缘范式要点(回顾)

摘自 `docs/Palantir架构与流程详解.md`,Palantir 的信任基础是三件贯穿全层的事:**血缘、版本、权限**。与本文最相关的是:

| 维度 | Palantir 做法 | 本质 |
|---|---|---|
| **血缘(Lineage)** | 每个 Dataset、每个转换步骤、甚至**列级**都自动记录来源和去向,形成全局 DAG;点击任一点可反查上游全链;用于审计、影响分析、根因定位 | 血缘是**基础设施**,不是事后补的报表 |
| **Action 天然带审计** | 本体 Action 执行时可改对象属性、创建/删除对象、触发外部系统,天然带**权限校验 + 审计 + 血缘**,每次操作留痕可回溯 | 操作 → 审计 → 血缘 是**原子绑定**的 |
| **人在环(Human-in-loop)** | AI 提议的 Action 可要求人工批准才执行,全程留痕 | 决策要扛得住监管的 "why?" |

一句话:**Palantir 的血缘不止画"表→任务→表"的数据流向,连"谁基于什么证据对这个表做了什么操作"也在图里。**

## 2. Semantica 调研(自称 "Open Source Palantir for AI Agents")

### 2.1 项目概况

| 项 | 内容 |
|---|---|
| 仓库 | `github.com/semantica-agi/semantica`(原名 Hawksight-AI),PyPI 同名,`pip install semantica`,MIT,~1K stars |
| 定位 | Graph-Native 语义层:为 LLM/Agent 提供知识图 + 确定性推理 + 全程溯源 |
| 离线确定性 | 图构建/推理/溯源不需要 LLM,可审计、可复现 |
| 架构管线 | Sources → Ingest → Extract(NER/关系/事件)→ Conflict Detection → Dedup → Knowledge Graph → [Ontology · Reasoning · Provenance · Decisions] → 导出/REST/MCP/CLI |

### 2.2 与审计血缘直接相关的四个能力

1. **Registry = 实时审计日志**(`semantica.registry`):每次图变更都写审计日志——谁、何时、改了哪个节点/边。
2. **Decision Records = 决策留痕**(`semantica.decisions`):`record_decision` 把每次决策记为一等公民;`trace_decision_chain` 可追溯整条因果链(这条决策引用了哪些证据、哪个上游决策、影响下游)。**这是"决策链"的标准实现**。
3. **PROV-O Lineage**(`semantica.provenance`,W3C PROV-O 标准):每个 fact/实体都有溯源视图——数据从哪个源来、经过什么推理/合并、谁改过。审计产物可导出 JSON/CSV/RDF。
4. **人在环**:SHACL 约束 + 冲突检测 + 合规规则,配合决策记录形成 "AI 提议 → 规则校验 → 留痕"。

### 2.3 与我们(dataMaster)的差距对照

| 维度 | Semantica | 我们(现状) | 差距 |
|---|---|---|---|
| 操作留痕 | Registry 每次图变更留痕,标准 PROV-O | `ONT_ACTION_EXECUTION` 全链路留痕(自造状态机,非标准) | 留痕有,标准缺 |
| 决策链 | Decision Records 一等公民,`trace_decision_chain` | 无 parentExecutionId/traceId 字段 | **不存在** |
| 血缘贯穿操作 | PROV-O Lineage 关联到每个 fact/decision | 动作执行**不写 Neo4j** | **缺口** |
| 审计导出 | JSON/CSV/RDF | 表查询 | 普通表查询,足够用 |

**结论**:值得借鉴的不是 Semantica 的 Python 代码(它与 Java 8 后端是两套运行时),而是它的**审计范式**——「操作/执行记录 → 血缘图 + 决策链指针」。

## 3. 我们当前的实际状态(代码实证)

### 3.1 Neo4j 血缘基建:骨架齐,没接线

Neo4j 子系统位于 `datamaster-common/datamaster-common-base`,共 10 个 Java 类,结构完整:

```
com.datamaster.neo4j
├── config/   Neo4jProperties(spring.data.neo4j 前缀)、MultiTxManagerConfig(双事务管理器)
├── node/     TableNode(@Node("Table") 唯一键 tableName+datasourceHostPort)、
│             TaskNode(@Node("Task") 业务键 taskId,type:1离线/2实时/3开发/4作业)
├── rel/      TableToTaskRel(TABLE_TO_TASK 表被任务读)、TaskToTableRel(TASK_TO_TABLE 任务写表)
├── repository/ TableRepository、TaskRepository(findLineage Cypher 一层血缘)
├── dto/      LineageDTO(currentTable/tasks/tables/rels)
└── service/  LineageDataService(save/saveTable/deleteTask/lineage/deletdAll)
```

- 启动装配 ✅:`DataMasterApplication.java` L29-30 有 `@EnableNeo4jRepositories` + `@EntityScan`(com.datamaster.neo4j)。
- **运行配置 ❌:`application*.yml`(application / -dev / -prod)中没有任何 `spring.data.neo4j` 配置段**(全项目 grep 零命中)→ 当前运行时 Neo4j 实际不可用。

### 3.2 集成(ETL)任务血缘:完全没进 Neo4j ★用户关注点①

- `LineageDataService` 全项目**唯一业务引用**在 `AssetsAssetServiceImpl.java`(L182 注入,L1519 调用),且是**只读查询**:

- `datamaster-collector`(ETL/集成模块)grep `lineage` **零命中**;ETL 主链路 `CollectorEtlTaskServiceImpl.publishTask`(L1531)→ `startCollectorEtlTask`(L1008)→ `CollectorEtlTaskInstanceServiceImpl.execute`(L403)全程不触碰 LineageDataService。
- 前端佐证:`datamaster-ui/src/views/col/asset/detail/index.vue` L266 血缘 tab 被注释掉(`// { label: '资产血缘', name: '4', component: lineage }`),前端目前不展示血缘。

### 3.3 动作执行血缘:没进 Neo4j,无决策链 ★用户关注点②

- `ActionExecutionServiceImpl.java`(datamaster-ontology-core,586 行)import **无任何 neo4j/lineage 类**;整个 `datamaster-ontology` 模块 grep `neo4j|lineage` 零命中。唯一跨模块依赖是 `IAssetsTableGovernanceApiService`(权限校验)。
- 全链路 `submitExecution`(生成SQL+预演+快照)→ `approveExecution`/`rejectExecution` → `executeExecution`(二次校验+执行)只落一张 MySQL 表 `ONT_ACTION_EXECUTION`,**不写任何血缘**。
- `ActionExecutionDO` 字段:`actionId, ontologyId, executorId, spaceId, spaceCode, inputParams, generatedSql, previewResult, beforeData, status, approvalReason, approverId, approveTime, executeTime, errorMessage` + BaseEntity(id/creatorId/createTime 等)。
  - **无 `parentExecutionId` / `sourceExecutionId` / `traceId` 等任何链路字段 → 决策链概念不存在**。同一个 actionId 的多条执行彼此独立,只能靠 createTime 间接排序。

## 4. 改进方案

### 总原则

1. **不引入 Semantica/新框架**:纯 Java 8 方案,复用现有 Neo4j 骨架。
2. **血缘为可选项,失败不阻断主流程**:Neo4j 不可用时 `save` 失败只记日志,不影响 ETL 发布/动作执行成功。
3. **接线点选"确定性解析表信息"的代码**,不做 LLM/字符串猜表。
4. **先齐配置,再接线路,再上图谱**,三步独立落地。

---

### 4.0 前置:补齐 Neo4j 配置(所有方案的前提)

`application-dev.yml` / `application-prod.yml` 增加:

```yaml
spring:
  data:
    neo4j:
      uri: bolt://<host>:<port>
      username: neo4j
      password: <口令>
```

配置为**环境敏感信息**,不入库、不进 PR 明文(参考 AGENTS.md 安全约定)。可选:spring.profiles 区分 dev/prod,Neo4j 只在配置了 `spring.data.neo4j.uri` 时启用 —— 现有 `Neo4jProperties` 已是 `@ConfigurationProperties` 绑定,天然支持"没配就是不连"。

### 4.1 集成(ETL)任务血缘接入 Neo4j ★主线

**接线点**:`CollectorEtlTaskServiceImpl.publishTask`(L1531)首次发布/二次发布成功后,任务定义落入 DolphinScheduler 的同时写血缘。若改执行回调(`CollectorEtlTaskInstanceServiceImpl`)则可顺带记录 executeTime/状态,但**结构血缘在发布时就能确定**,优先发布时写入。

**数据来源(已实证可用)**:
- `TaskConverter.buildEtlTaskParams(...)` 产出的 `mainArgs` 中含 `reader`/`writer`/`readerList`/`writerList`,每项的 `parameter` 里有 `datasourceId` 和表名(`connectionTable(param)` 提取)。
- 数据源 host/port/类型:`IDatasourceApiService` 按 `datasourceId` 解析(`TaskConverter.resolveDsDatasourceId` 已是现成用法)。
- 增量任务:`FlinkxIncrementalConfig` 已带 `sourceDatasourceId / sourceTableName / targetDatasourceId / targetTableName`(TaskConverter L1426-1436 构造),可直接复用。

**落点设计**:在 `datamaster-common-base` 的 `LineageDataService` 旁新增一个装配器(避免 collector 模块直接拼 Neo4j 数据结构):

```java
public class EtlLineageAssembler {
    // 输入:mainArgs(reader/writer/readerList/writerList)+ 任务信息 + IDatasourceApiService
    public List<TableNode> buildReaderTables(Map<String,Object> mainArgs) { ... }
    public List<TableNode> buildWriterTables(Map<String,Object> mainArgs) { ... }
    public TaskNode buildTaskNode(Long taskId, String taskCode, String name) { ... }
}
```

**调用链改造**(collector-core):
```java
// CollectorEtlTaskServiceImpl.publishTask(...) 发布成功后追加:
try {
    List<TableNode> readers = etlLineageAssembler.buildReaderTables(mainArgs);
    List<TableNode> writers = etlLineageAssembler.buildWriterTables(mainArgs);
    TaskNode taskNode = etlLineageAssembler.buildTaskNode(taskDO.getId(), taskCode, taskDO.getName());
    lineageDataService.save(readers, writers, taskNode);   // 已支持 upsert 合并关系
} catch (Exception e) {
    log.warn("血缘写入失败(不影响发布):{}", e.getMessage());
}
```

**删除联动**:`CollectorEtlTaskServiceImpl` 删除任务处追加 `lineageDataService.deleteTask(taskId)`,同样 try/catch 降级。

**图模型(复用现有,零新节点)**:
```
(Table:源表) --TABLE_TO_TASK--> (Task:1离线) --TASK_TO_TABLE--> (Table:目标表)
```

**验收**:发布一个 MySQL→MySQL 全量任务后,Neo4j 出现 source → task → target 三角;二次发布同一任务关系不重复(TaskNode 按 taskId 先删后建,Table 按唯一键合并,`LineageDataService.save` 已实现该语义)。

### 4.2 动作执行血缘接入 Neo4j ★主线

**接线点**:`ActionExecutionServiceImpl.executeExecution(...)`(仅 APPROVED 可执行的那段)执行成功后追加血缘写入;审批通过那一刻也可加一条"已批准"标记(可选)。

**图模型(需扩展,复用 Table 节点 + 新增执行节点)**:

```
(Table:概念物理表) <--[ACTION_EXECUTED]-- (ActionExecution)
   属性:executionId / actionId / actionName / actionType(CREATE|UPDATE|DELETE|QUERY)
         executorId / status / generatedSql / executeTime
```

- **不新增 Table 类型的节点**:动作操作的就是概念绑定的物理表(`ONT_CONCEPT_TABLE` → datasourceId/tableName),通过 `IDatasourceApiService` 解析 host/port 后仍归入 `(Table)` 节点,与 ETL 血缘的"表"统一——**图和查询链路共用 `TableRepository`/`dataLineage` 不需要改**。
- **新增一个 `@Node("ActionExecution")` 节点 + 关系 `ACTION_EXECUTED`**,建议放 `datamaster-common-base` 的 neo4j 包(与现有骨架同包),或复制现有 node/rel/repository/service 的写法。

**落点设计**(新增类,最小改动):
```java
// ActionExecutionDO 已含执行全部审计字段,天然可映射
public void writeActionLineage(ActionExecutionDO exec, ConceptTableDO conceptTable, DatasourceRespDTO ds) {
    TableNode tableNode = TableNode.builder()
            .tableName(conceptTable.getTableName())
            .datasourceHostPort(ds.getHost() + ":" + ds.getPort())
            .datasourceName(ds.getName()).datasourceType(ds.getType()).build();
    ActionExecutionNode execNode = ActionExecutionNode.builder()
            .executionId(exec.getId()).actionId(exec.getActionId())
            .actionName(actionName).actionType(actionType)
            .executorId(exec.getExecutorId()).status(exec.getStatus())
            .generatedSql(exec.getGeneratedSql()).executeTime(exec.getExecuteTime()).build();
    actionExecutionRepository.save(relation(execNode, tableNode));
}
```

**调用链改造**(ontology-core):
```java
// executeExecution(...) 真实执行成功分支末尾:
private void writeActionLineageSilently(ActionExecutionDO exec) {
    try {
        ConceptTableDO ct = conceptTableMapper.selectByConceptId(exec.getAction().getConceptId()); // 第一张物理表
        DatasourceRespDTO ds = datasourceApiService.getDatasourceById(ct.getDatasourceId());
        actionLineageService.write(exec, ct, ds);
    } catch (Exception e) { log.warn("动作血缘写入失败(不影响执行):{}", e.getMessage()); }
}
```

**未接线的动作类型**:文件型数据源(Kafka/文件)无物理表,跳过;动作 SQL 里写多个表的情况第一版只记概念主表,后续可跟进解析 generatedSql 中的表引用。

### 4.3 决策链追溯 ★主线

**目标**:同一条业务线(如"把订单价格上调 5%")的多轮 提交→审批→执行 能被串起来,追溯"这次改单的决策依据/上一次执行是谁改的"。

**方案(轻量,优先)**:仅靠 MySQL 扩展,不动 Neo4j:

`ONT_ACTION_EXECUTION` 增加一个可空字段:
```sql
ALTER TABLE ONT_ACTION_EXECUTION ADD COLUMN PARENT_EXECUTION_ID BIGINT NULL COMMENT '上一轮相关执行ID,形成决策链';
```

`ActionExecutionDO` 增加 `parentExecutionId`;
`ActionExecutionServiceImpl.submitExecution(...)` 构造记录时:
```java
// 同一 actionId 下最近一次非失败(EXECUTED/APPROVED/PENDING)的执行作为父节点
Long parentId = actionExecutionMapper.selectLatestExecutedByActionId(actionDO.getId());
exec.setParentExecutionId(parentId);
```

查询:`getExecutionById` 后按 `parentExecutionId` 链式上溯,或新增接口 `List<ExecutionRespVO> getExecutionChain(Long executionId)`(沿 parentExecutionId 递归/循环收集)。

**进阶(可选,对齐 Semantica trace_decision_chain)**:在 4.2 的 `ActionExecution` 节点上加 `parentExecutionId` 属性,用 Cypher `MATCH (a:ActionExecution)-[:CHAIN]->(prev)` 在图上画完整决策链。第一版建议只做 MySQL 链(成本低、足够业务审计),图上的 CHAIN 关系列为后续增强。

### 4.5 可插拔开关设计(已落地):没装 Neo4j 也能跑

**核心目标(用户要求逐字)**:「血缘要是可插拔的即弄个环境变量是否开启血缘记录 没有开启不安装neo4j的时候不影响etl任务和动作执行;但是动作执行要有基本的记录 即生成记录 显示修改前和修改后的数据(做到可溯源回退)」。

**开关定义**(`application.yml`):
```yaml
datamaster:
  lineage:
    enabled: ${LINEAGE_ENABLED:false}   # 环境变量 LINEAGE_ENABLED,默认关闭
```

**关闭时的装配行为(全链路条件装配,@ConditionalOnProperty)**:

| 类 | 条件 |
|---|---|
| `Neo4jLineageConfig`(@Configuration) | `havingValue=true` 时启用,内含 `@EnableNeo4jRepositories(basePackages="com.datamaster.neo4j.repository")` + `@EntityScan(basePackages="com.datamaster.neo4j.node")` |
| `MultiTxManagerConfig.neo4jTransactionManager` | 同条件;`jdbcTransactionManager` 无条件且 `@Primary` |
| `LineageDataService` | 类级 `@ConditionalOnProperty`(开关关时该 Bean 不存在) |
| `DataMasterApplication` | **移除**硬编码 `@EnableNeo4jRepositories` / `@EntityScan`(仅保留 `@SpringBootApplication`) |

**注入侧全部可空 + 判空降级(开关关时无 Neo4j Bean 也不报错)**:
- `AssetsAssetServiceImpl`(assets-core):`lineageDataService` 注入 `@Autowired(required=false)`,`dataLineage()` 判空返回空 `LineageDTO`;
- `CollectorEtlTaskServiceImpl`(collector-core):`lineageDataService` 注入 `@Autowired(required=false)`;`writeTaskLineageSilently` / `deleteTaskLineageSilently` try/catch 静默降级;
- `ActionExecutionServiceImpl`(ontology-core):`lineageDataService` 注入 `@Autowired(required=false)`;`writeActionLineageSilently` try/catch 静默降级。

**效果**:`LINEAGE_ENABLED=false`(默认)或未部署 Neo4j 时,启动不装配任何 Neo4j Bean,ETL 发布/删除、动作 提交→审批→执行 全部照常(行为等价于改造前);置为 `true` 且配好 `spring.data.neo4j` 后才启用血缘写入。

### 4.6 动作执行记录增强(已落地):显示修改前/修改后,可溯源回退

**执行逻辑完全不变**(用户要求逐字:「权限校验 预执行 页面审批后 真正提交事务」):
`submitExecution`(权限校验 + 预执行 dry-run + BEFORE_DATA 快照)→ `approveExecution` 页面审批 → `executeExecution`(二次权限校验 + 真正提交事务)。

**BEFORE_DATA / AFTER_DATA 双快照**:
- `ActionExecutionDO` / `ExecutionRespVO` 新增 `afterData` 字段;`ONT_ACTION_EXECUTION` 新增 `AFTER_DATA JSONB`(`sql/update_20260829_ont_action_execution_after_data.sql`;新装库 `sql/ontology_tables.sql` 建表语句同步);
- `executeExecution` DML 成功分支捕获执行后快照,按动作类型区分:
  - **UPDATE**:`convertToSelect(sql)` 重查,记录更新后的新值;
  - **DELETE**:执行后重查为空集 `[]`(行已删),**回退 = 按 BEFORE_DATA 重 INSERT**;
  - **CREATE**:`buildSelectByPk` 按主键参数回查新插入行;
- 快照捕获失败仅记 warn,`AFTER_DATA` 为 NULL,不影响执行记录本身。

**动作血缘(Neo4j,可选增强)**:新增 `ActionExecutionNode`(@Node("ActionExecution"))+ `ActionExecutionRepository`;`LineageDataService.saveActionExecution(...)` 写入;`executeExecution` 执行后 `writeActionLineageSilently` 落节点(executionId/actionId/actionName/actionType/tableName/status/executeTime/…),失败仅记 warn。受 `LINEAGE_ENABLED` 开关控制,插拔即用。

## 5. 落地顺序与验收清单

**关键风险与对策**:
- Neo4j 宕机时不能让 ETL 发布/动作执行失败 → 所有血缘写入 try/catch 降级(方案已内置)。
- 老任务无血缘数据 → 图从改造后新任务开始积累,不回溯。
- 事务边界 → 血缘用 `@Transactional("neo4jTransactionManager")`(现有 MultiTxManagerConfig 已支持),与 JDBC 事务分离,不参与主库回滚。

## 6. 一句话总结

Palantir 的护城河是「血缘/版本/权限贯穿全层」,Semantica 把这套做成了 PROV-O + Decision Records 的开源范本;**我们现状是骨架齐全但零接线**——ETL 血缘写方法无调用者、动作执行零 neo4j 依赖、决策链字段不存在。改进方案按 配置 → ETL 接线 → 动作接线 → 决策链 → 前端 五步落地,全部复用现有 Neo4j 骨架与 `ONT_ACTION_EXECUTION` 审计字段,失败降级,不引入新框架。
