# 数据开发当前实现说明

## 结论

当前项目里的“数据开发”不是一套完全独立的后台实现，而是复用了 collector 模块的 ETL 任务体系。

数据开发通过 `type = "3"` 和数据集成任务区分；数据集成离线任务通常是 `type = "1"`。两者共用 `/col/etlTask` 这一组接口、任务表、节点表、发布逻辑、调度逻辑和 DolphinScheduler 对接能力。

一句话概括：

> 数据开发 = 数据集成/ETL 任务后台 + `type=3` + SQL/Shell/存储过程/SparkSQL 组件 + DolphinScheduler 执行调度。

## 前端入口

数据开发前端页面主要在：

- `datamaster-ui/src/views/col/task/developTask/index.vue`
- `datamaster-ui/src/views/col/task/developTask/add/add.vue`
- `datamaster-ui/src/views/col/task/developTask/detail/index.vue`

数据集成前端页面主要在：

- `datamaster-ui/src/views/col/task/integratioTask/index.vue`
- `datamaster-ui/src/views/col/task/integratioTask/edit/index.vue`
- `datamaster-ui/src/views/col/task/integratioTask/detail/index.vue`

数据开发列表查询时会固定传入：

```js
p.type = "3";
```

新增数据开发任务时也会传：

```js
type: "3"
```

因此前端层面是通过 `type=3` 把数据开发任务从同一套 ETL 任务接口里筛出来。

## 后台入口

数据开发后台复用数据集成任务 Controller：

- `datamaster-collector/datamaster-collector-biz/src/main/java/com/datamaster/module/collector/controller/admin/etl/CollectorEtlTaskController.java`

主要接口包括：

- `GET /col/etlTask/getCollectorEtlTaskPage`：查询任务列表
- `POST /col/etlTask/createEtlTaskFront`：新增任务草稿
- `POST /col/etlTask/createEtlTaskFrontPostposition`：保存任务配置
- `GET /col/etlTask/updateQuery/{id}`：查询任务详情
- `POST /col/etlTask/publishTask`：发布任务到 DolphinScheduler
- `POST /col/etlTask/unpublishTask`：从 DolphinScheduler 卸载任务
- `PUT /col/etlTask/startDppEtlTask/{id}`：执行一次任务
- `POST /col/etlTask/updateReleaseJobTask`：任务上下线
- `POST /col/etlTask/updateReleaseSchedule`：调度上下线
- `POST /col/etlTask/releaseTaskCrontab`：修改调度周期

核心 Service 实现在：

- `datamaster-collector/datamaster-collector-biz/src/main/java/com/datamaster/module/collector/service/etl/impl/CollectorEtlTaskServiceImpl.java`

## 执行引擎判断

数据开发不是默认全部用 Spark 执行 SQL。

实际执行方式取决于保存任务时的 `taskType` 和 `componentType`：

| componentType | taskType | 含义 | 执行方式 |
| --- | --- | --- | --- |
| `51` | `SQL` | SQL开发 | DolphinScheduler SQL 任务，基于配置的数据源执行 SQL |
| `52` | `PROCEDURE` | 存储过程开发 | DolphinScheduler 存储过程/SQL 类任务，调用关系型数据库存储过程 |
| `53` | `SPARK` | SparkSql开发 | Spark 执行 SQL |
| `54` | 通常为 Shell 相关类型 | SHELL开发 | 执行 Shell 脚本 |

因此只有 `componentType=53` 的 SparkSql 开发可以认为是 Spark 执行 SQL。普通 SQL 开发不是 Spark，而是走数据库连接执行 SQL。

## 页面控制台显示 Flink 的原因

数据开发页面控制台里出现 Flink，不一定代表实际任务由 Flink 执行。

当前前端存在几处 Flink 相关的静态展示或预留逻辑。

### 控制台树写死了 FlinkSubmit

文件：

- `datamaster-ui/src/components/SqlEditor/console/index.vue`

其中控制台左侧树是静态数据：

```js
const treeData = ref([
  {
    label: "FlinkSubmit",
    value: "1",
    unit: "秒",
    children: [...]
  },
]);
```

所以页面控制台显示 `FlinkSubmit`，不是后端返回的真实执行引擎，而是前端写死的展示。

### SQL 编辑器默认注册 FlinkSQL 语法

文件：

- `datamaster-ui/src/components/SqlEditor/editor/index.vue`
- `datamaster-ui/src/components/SqlEditor/languages/flinksql/index.tsx`

编辑器默认语言和语法高亮使用了 `flinksql`，这会让页面表现上更像 FlinkSQL 编辑器。

### 配置面板预留了 FlinkSql 开发

文件：

- `datamaster-ui/src/components/SqlEditor/configView/index.vue`

其中预留了：

```js
{
  componentType: "55",
  label: "FlinkSql开发",
  taskType: "FLINK",
  id: "5",
  show: false,
}
```

但后端 `TaskComponentTypeEnum` 当前没有 `55`，`ComponentRegistry` 里也没有 FlinkSql 组件注册。因此这部分更像前端预留或半成品能力，目前不能视为完整可用的 FlinkSQL 数据开发实现。

## 和数据集成的关系

当前数据开发和数据集成的关系是：

- 后台共用 collector ETL 任务体系。
- 数据开发通过 `type=3` 区分。
- 数据集成通常通过 `type=1` 区分。
- 发布、卸载、调度、执行、实例日志等能力共用同一套后台服务。
- 数据集成页面更完整地提供输入、清洗、转换、输出等可视化组件。
- 数据开发页面更偏 SQL 编辑、模板、任务属性配置和执行。

因此不能简单说“数据开发已经被数据集成替换”，更准确是：

> 数据开发和数据集成共用同一套 ETL/调度底座，但在前端入口、类目、任务类型和可选组件上做了区分。

如果后续要收敛两套入口，建议保留统一的 ETL 后台，把数据开发和数据集成作为不同任务类型管理，而不是直接删除数据开发入口。

## 建议收敛方向

后续可以将“数据流加工”能力主要收敛到数据集成中，数据开发只保留 SQL 执行和 Shell 执行等轻量执行类能力。

### 数据集成作为主入口

数据集成本身已经具备源端、目标端、字段映射、清洗、转换和输出能力。当前集成任务使用 FlinkX/Chunjun 执行时，也可以通过转换 SQL 表达复杂加工逻辑。

因此可以在数据集成中增强“自定义 `transformSql`”能力，用它承接原来数据开发中的大部分数据加工场景。

从执行语义看，数据集成配置：

- source 数据源
- sink 数据源
- 字段映射
- 清洗转换
- 自定义 `transformSql`

本质上可以等价生成类似下面的 FlinkSQL 作业结构：

```sql
CREATE TABLE source (...);
CREATE TABLE sink (...);

INSERT INTO sink
SELECT ...
FROM source;
```

也就是说，数据集成的可视化配置可以视为 FlinkSQL 作业的结构化表单表达。普通用户通过表单配置源、目标和转换，高级用户通过自定义 `transformSql` 编写更复杂的 SQL 转换逻辑。

### 数据开发保留执行类任务

数据开发不再承担输入、输出、链路转换建模，这些能力交给数据集成。

数据开发建议只保留：

- SQL 执行：单库查询、DDL、DML、临时处理、运维 SQL。
- 存储过程执行：可归入 SQL 执行能力，或作为 SQL 类型的一个子类型。
- Shell 执行：脚本、外部命令、补充调度动作。

这样模块职责更清晰：

| 模块 | 建议职责 |
| --- | --- |
| 数据集成 | 数据同步、字段映射、清洗转换、自定义 `transformSql`、FlinkX/Chunjun 作业 |
| 数据开发 | SQL 执行、存储过程执行、Shell 执行、轻量脚本任务 |
| 作业任务 | 多任务编排、子任务、依赖调度 |

### 具体调整建议

1. 在数据集成转换节点中正式增加“自定义 `transformSql` / 高级 SQL 模式”。
2. 数据集成支持查看系统根据源端、目标端、字段映射生成的 SQL 片段，便于排查和高级编辑。
3. 数据开发页面隐藏或移除 SparkSQL/FlinkSQL 这类链路加工入口，只保留 SQL、存储过程和 Shell。
4. 菜单和文案上弱化“数据开发 = 数据加工开发”的含义，调整为“SQL/脚本执行”类入口。
5. 后台继续复用 collector ETL 任务底座，通过 `type` 和 `componentType` 区分任务形态，避免新增一套重复后端。

这样收敛后，数据集成负责“采集 + 转换 + 落库”的完整链路，数据开发负责独立 SQL/脚本执行，两者边界会更清楚，也能减少功能重叠。

# 改造任务跟踪

## 任务一：数据源同步到 DolphinScheduler 源中心

### 描述
将 DataMaster 数据源模块的数据源同步到 DolphinScheduler 的源中心，并在同步时调用 DS 的测试连接接口，验证 DS 是否能连通该数据源。

### 目的
解决 DataMaster 数据源和 DS 数据源不一致的问题。如果不同步，DS 执行 SQL/Shell/Python 任务时拿不到数据源连接信息，需要用户在 DS 源中心手工重配一遍。同步后自动测试连接，提前发现网络不通、账号不对等问题。

### 涉及模块
- datamaster-assets — 数据源管理
- datamaster-api-ds — DS HTTP API 封装
- datamaster-collector — 同步触发入口

### 进度

| 步骤 | 状态 | 说明 |
|------|------|------|
| 分析 DS 源中心 API（创建数据源、测试连接） | 已完成 | API 已封装：CREATE_DATASOURCE(35)、TEST_CONNECT_DATASOURCE(36)、QUERY_DATASOURCE_LIST(37) |
| DS API 层 `DsDatasourceServiceImpl` | 已完成 | `createDatasource` 和 `testConnect` 两个方法都已实现 |

## 任务二：执行引擎调整为 SQL、存储过程、Shell、Python

### 描述
