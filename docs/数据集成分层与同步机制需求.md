# 数据集成分层与同步机制需求记录

最后更新：2026-10-16

## 当前实现状态（2026-10-16）

本文中的逻辑集成节点、来源治理字段和分层发布链路已经开始落地：

- 前端以一个逻辑节点表达「输入 → 可选转换 → 输出」，支持 ODS / DWD / DWS；逻辑节点可以继续作为下游节点输入。
- `source_table`、`write_time` 由发布器强制开启并由 Flink SQL 自动生成；`source_datasource`、`source_database`、`source_task`、`source_batch`、`source_natural_key`、`source_row_hash`、`source_update_time`、`record_op` 均为可选。
- A/B → ODS 后再合并到 DWD 时，画布保存 A→C、B→C 依赖，发布时展开为多个 DolphinScheduler/FlinkX 数据节点，并递归继承已经落库的来源字段。
- 普通节点引用 `NODE_OUTPUT` 时强制继承上游目标数据源；`UNION_ALL` 合并节点要求所有上游目标表位于同一个读取数据源。
- 元数据探查和质量检查复用现有任务，通过配置选择任务 ID，发布时分别追加前置 / 后置 HTTP 节点；质量任务当前语义仍是异步触发，不等同于质量门禁。
- 元数据探查 / 质量检查开关一旦启用，必须绑定已有任务 ID；前后端在保存 / 发布阶段都会校验，避免静默跳过。
- 目标表结构目前仍需提前包含治理列，发布器不会隐式修改生产表结构；发布前会读取目标表结构并校验治理列是否存在。
  完整 Maven 编译和真实 DolphinScheduler/FlinkX 运行验证仍应在集成环境执行。

本文记录数据集成（`datamaster-collector`，任务 `type=1`）在引入**原始层 / 明细层**分层后的四项需求：

1. 原始层要增加「数据来源」字段和「写入时间」字段；
2. 明细层同步过程要有「无则插入、有则更新」（Upsert）机制；
3. 多个来源字段同名时，以哪张表为主（优先级）；
4. 前端配置里要有对应标志。

本文记录需求、配置模型与发布展开规则；具体代码改造按本文模型逐步落地。

## 0. 现状基线（必须先对齐）

### 0.1 数据集成任务链路

数据集成复用 collector ETL 任务体系，前端入口：

- 列表：`datamaster-ui/src/views/col/task/integratioTask/index.vue`
- 编辑：`datamaster-ui/src/views/col/task/integratioTask/edit/index.vue`
- 节点组件：`datamaster-ui/src/views/col/task/integratioTask/components/`

链路为「输入节点 → 转换节点 → 输出节点」，后端转化为 ChunJun / FlinkX Job JSON，经 DolphinScheduler 调度执行。

### 0.2 已有写入模式

输出节点已存在写入模式 `writeModeType`（`output/tableForm.vue`）：

| 值 | 名称 | 当前行为 |
| --- | --- | --- |
| `1` | 全量 | 写入前对目标表执行 truncate 前置 SQL，再整表写入（`FlinkxJson.java` 中 `trainToJdbcTruncateTable`） |
| `2` | 追加 | 纯 append 写入 |
| `3` | 增量更新 | 依赖主键做 update/insert；非 Doris 数据源必须在「更新主键字段」中勾选主键 `selectedColumns` |

后端落点：

- `datamaster-collector/datamaster-collector-core/src/main/java/com/datamaster/module/collector/utils/datax/FlinkxJson.java`
  - `writeMode = readerProperty.trainToJdbcWriteMode(selectedColumns, writeModeType, dbType)`
- `datamaster-collector/datamaster-collector-core/src/main/java/com/datamaster/module/collector/utils/ds/component/DBWriterComponent.java`
  - 注释口径：`writeModeType`：`1 全量，2 追加写，3 增量更新`；`selectedColumns`：增量更新主键

### 0.3 已有合表输入能力

`datamaster-ui/src/views/col/task/integratioTask/components/input/tableMerge.vue` 支持「合表」：把多个**结构相同**的源表合并，输出字段列表（`tableFields` / `columns`），每个源表可配 `table_name` 与 `where`。

关键缺口：**合表后没有来源标识字段**，无法区分每一行来自哪张源表。

### 0.4 ingestion 模块已有 Upsert（对照参考）

`datamaster-ingestion` 已实现「无则插入、有则更新」：`UPSERT` 使用 Doris 原生 `ON DUPLICATE KEY UPDATE`，并以 `key-columns` 指定主键，冲突策略 `UPSERT / INSERT / SKIP / ERROR` 可配。本文的明细层 Upsert 需求应与该口径尽量统一。

## 1. 需求一：原始层增加「数据来源」字段

### 1.1 目标

原始层（贴源层 / ODS）每一条记录都要能回答：**这行数据来自哪个数据源、哪张源表、哪个集成任务 / 批次**。用于溯源、去重、以及后续明细层冲突仲裁。

### 1.2 需求内容

- 原始层每个集成任务的输出表，除业务字段外，必须附带来源标识字段；
- 该字段在写入时由集成任务自动补值（作为常量列 / 派生列注入），无需源表提供；
- 建议至少覆盖以下元数据：

| 含义 | 建议列名（待定） | 说明 |
| --- | --- | --- |
| 来源数据源 | `data_source` / `source_system` | 数据源 ID 或名称 |
| 来源库表 | `source_table` / `src_table` | 源库名.表名 |
| 来源任务 / 批次 | `source_task` / `etl_batch` | 集成任务 ID 或本次运行批次 |
| 写入时间 | `write_time` | 写入时刻 |

本期实现统一采用 `sourceMetadata` 配置，默认字段名为：

示例配置：

```json
{
  "sourceMetadata": {
    "enabled": true,
    "naturalKeyColumns": ["ID"]
  }
}
```

字段名可以在配置中覆盖，但不建议各任务自定义，避免 ODS 表无法统一查询。

| 字段 | 含义 | 生成方式 |
| --- | --- | --- |
| `source_datasource` | 来源数据源 ID | 任务配置常量 |
| `source_table` | 来源表名 | 单表输入取源表名，合表由每个 `UNION ALL` 分支注入 |
| `source_task` | 来源节点 / 任务标识 | 任务节点编码 |
| `source_batch` | 来源批次标识 | 由运行配置传入，可为空 |
| `write_time` | 写入时间 | Flink SQL `CURRENT_TIMESTAMP` |
| `source_natural_key` | 来源自然键技术标识 | `source_table + 源主键列` 的稳定 MD5；未配置源主键时不生成 |

`source_natural_key` 不是业务主键，也不替代明细层 Upsert 主键。它用于 ODS 溯源、同源行定位和重跑去重。普通单表输入建议启用；合表输入也建议启用，但必须把 `source_table` 纳入 hash，否则不同来源表的相同业务主键会发生碰撞。没有可靠源主键时不应使用行内容全部拼接来冒充自然键，因为业务字段变化会导致标识变化。

> 列名与数量为待确认项（见第 5 节）。

### 1.2.1 当前可配置字段分组

逻辑集成节点的字段分为“业务字段”“来源治理字段”“运行配置”三组。只有来源治理组中的
`source_table`、`write_time` 是原表落库的强制字段；其余来源治理字段均为可选，未勾选时不加入
reader / transformer / writer 的字段列表。

| 分组 | 字段 | 必须性 | 配置位置 | 生成或传递方式 |
| --- | --- | --- | --- | --- |
| 业务字段 | `columns` / `tableFields` | 必须 | 逻辑节点输入 | 源表探查后保存，作为 FlinkX reader 的真实业务列 |
| 业务字段 | `targetColumns` / `target_columns` | 可选（未配置时按输入字段） | 逻辑节点输出 | 作为 writer 目标列映射 |
| 业务字段 | `writeModeType` | 必须有默认值 | 逻辑节点输出 | `1` 全量、`2` 追加、`3` Upsert |
| 业务字段 | `selectedColumns` | Upsert 时必须（Doris 由表模型约束） | 逻辑节点输出 | 传给 FlinkX writer 作为更新主键 |
| 来源治理 | `source_table` | **必须** | `taskParams.pipelineNode.sourceMetadata` | 单表取源表名；合表由每个 UNION ALL 分支注入；下游连续输出保留上游值 |
| 来源治理 | `write_time` | **必须** | `taskParams.pipelineNode.sourceMetadata` | Flink SQL `CURRENT_TIMESTAMP`，每层写入时重新生成 |
| 来源治理 | `source_datasource` | 可选 | `sourceMetadata.includeSourceDatasource` | 注入源数据源 ID |
| 来源治理 | `source_database` | 可选 | `sourceMetadata.includeSourceDatabase` | 注入源数据库名 |
| 来源治理 | `source_task` | 可选 | `sourceMetadata.includeSourceTask` | 注入逻辑节点 / 任务标识 |
| 来源治理 | `source_batch` | 可选 | `sourceMetadata.includeSourceBatch` | 由运行批次上下文传入，可为空 |
| 来源治理 | `source_natural_key` | 可选 | `sourceMetadata.includeNaturalKey` + `naturalKeyColumns` | `MD5(source_table + 源主键列)`；没有可靠源主键时不生成 |
| 来源治理 | `source_row_hash` | 可选 | `sourceMetadata.includeRowHash` | 仅对业务字段计算行内容 Hash，不包含任何来源治理列或 `write_time` |
| 来源治理 | `source_update_time` | 可选 | `includeSourceUpdateTime` + `sourceUpdateTimeSourceColumn` | 从源表真实更新时间列映射 |
| 来源治理 | `record_op` | 可选 | `includeRecordOp` + `recordOpSourceColumn` | 从 CDC 操作列映射 |
| 运行配置 | `schemaMonitoring` | 可选 | 逻辑节点输入 / 节点级配置 | 选择已有元数据探查任务，发布时生成前置 HTTP 节点 |
| 运行配置 | `qualityConfig` | 可选 | 逻辑节点输出 / 目标表配置 | 选择已有质量检查任务，发布时生成后置 HTTP 节点 |

前端保存时应保留完整的 `sourceMetadata` 配置，即使可选开关关闭也不要删除配置值；后端发布
只根据开关决定是否生成对应列。这样可以在编辑任务时稳定回显，也兼容后续重新开启字段。
启用 `source_update_time` 或 `record_op` 时必须同时选择对应的源端字段；自然键没有可靠源主键时则不生成。

### 1.2.2 元数据探查与质量检查的实现边界

- **元数据探查**：配置在 `pipelineNode.schemaMonitoring`（兼容 `input.schemaMonitoring`），只保存
  `enabled`、`onDrift`、`taskId`。`taskId` 对应现有元数据探查任务，不新增业务表字段。发布时由后端
  自动生成一个 DS `HTTP` 前置节点，调用 `/cat/taskExecutor/runExecuteTask/{taskId}`，并建立
  `探查 → 当前逻辑集成节点` 的依赖。探查结果仍写入元数据任务自己的结果表。
- **质量检查**：配置在 `pipelineNode.output.qualityConfig`，只保存 `enabled`、`onFailure`、`taskId`
  等运行参数。发布时由后端自动生成一个 DS `HTTP` 后置节点，调用
  `/quality/qualityTaskExecutor/runExecuteTask/{taskId}`，并建立 `当前逻辑集成节点 → 质量检查` 的依赖。
  质量结果写入质量任务自己的结果表，不回写 ODS / DWD 业务表。
- 当前两个执行接口都是异步提交：HTTP 节点成功只表示“已触发任务”，不表示探查或质量规则已经通过。
  因此 `onFailure=FAIL` 目前不能阻断 DS 后续节点；若需要真正门禁，应新增同步轮询 / 结果判断节点，
  仍复用同一元数据探查任务和质量检查任务，不改变逻辑节点的前端模型。

### 1.3 现状缺口

- 输出节点当前只写入 `columns` / `target_columns`，不注入额外来源列；
- 合表输入节点（`tableMerge.vue`）合并多张源表后，输出字段只有 `columnName`，**没有来源列**，这是最主要的缺口；
- 因此目前原始层无法区分多来源数据。

### 1.4 初步方向

- 在输入节点配置 `sourceMetadata`，由 Flink SQL transformer 自动追加来源列，writer 侧同步补齐目标字段；旧 `FlinkxJson` 路径不能作为唯一改造点，当前主链路是 `Component.parse2` + `FlinkxEtlTaskConverter`；
- 每个输入 / 合表源表可配置「来源标识值」（如源表名或自定义标签）；
- 目标表结构需预留来源列（建表 / 创建临时表时一并带上）；自动建表逻辑还需补充对派生元数据列的识别。

## 2. 需求二：明细层「无则插入、有则更新」（Upsert）

### 2.1 目标

明细层（DWD）同步过程必须支持 Upsert：

- 目标表**无该主键记录 → 插入**；
- 目标表**已有该主键记录 → 更新**；
- 重复执行同一同步任务不产生重复行。

### 2.2 需求内容

必须明确定义三件事：

1. **唯一键（业务主键）**：以哪些列判定「同一条记录」。支持单列 / 复合主键；
2. **更新列范围**：命中后是整行覆盖，还是只更新指定非主键列；
3. **冲突时机与语义**：同批次内重复、跨批次重复、以及并发写入时的行为。

### 2.3 与现有机制的关系

- 现有 `writeModeType = 3 增量更新` 已具备 Upsert 雏形：非 Doris 库靠 `selectedColumns` 主键 + `writeMode` 实现 update/insert；
- Doris 数据源当前不要求前端选主键，collector 仅生成 writer 的 `update` 模式；`datamaster-ingestion` 的 `ON DUPLICATE KEY UPDATE` 不能直接视为 collector 已具备的语义，仍需按 Doris 表模型和 ChunJun writer 实际联调；
- 需求是把这条链路**从「可选能力」升级为「明细层强制能力」**，并统一非 Doris 与 Doris 的契约。

### 2.4 现状缺口

- 非 Doris 库若未正确勾选 `selectedColumns`，前端允许 `writeModeType=3` 但缺少主键时会拦截（`output/tableForm.vue` 已做校验）；Doris 则完全依赖表模型，前端无标志；
- 缺少「更新列范围」配置：当前无「整行覆盖 / 仅更新部分列」的开关；
- 主键来源未与原始层「来源字段」协同：多来源合表后主键可能重复，需要来源字段参与唯一性判定。

### 2.5 初步方向

- 明细层输出节点默认要求配置唯一键；无唯一键不允许发布为明细层 Upsert 任务；
- 明确「更新列 = 全列覆盖」还是「排除主键 / 来源列」，作为前端可选项；
- 与 ingestion 的 `key-columns` + `UPSERT` 语义对齐，避免两套冲突策略。

## 3. 需求三：同名字段冲突时以哪张表为主

### 3.1 场景

明细层把多个来源（多张源表 / 多个输入节点）通过 Join 合并为一张宽表时，会出现**字段同名**（如多个来源都有 `name`、`status`、`update_time`）。

注意：当前“合表”节点实际是结构相同表的 `UNION ALL`，不是 Join。Union 场景不存在“主表覆盖从表”的字段级冲突；主表优先级需求应单独定义为“多表 Join / 宽表合并”能力，不能直接挂在现有 `tableMerge` 上。

需明确：**同名字段最终取哪个来源的值**。

### 3.2 需求内容

- 必须能指定「以哪张表为主」（主表 / 主来源），其余来源为从属；
- 主表优先级规则需明确：
  - 是否按**优先级数值**排序，高优先级覆盖低优先级；
  - 主来源该字段为空时，是「用空覆盖」还是「回退到次优先级来源」；
  - 是否需要按**时间戳**比较（仅当来源带更新时间时）。

### 3.3 参考设计（Palantir 冲突处理调研）

`docs/Palantir数据绑定与冲突处理调研.md` 的结论可直接借鉴：

- 冲突判定 = **主键定位到行 + 逐字段判优先**，是**字段级**优先级，不是整表级；
- 靠**分层优先级**规避覆盖，而不是靠落库时间先后；
- 命门是**稳定唯一主键**——这也与需求二的主键要求一致。

### 3.4 现状缺口

- 合表输入节点（`tableMerge.vue`）没有「主表 / 优先级」概念，多个同名字段无法区分；
- 字段映射组件（`output/fieldMap.vue`）只做来源字段 → 目标字段的映射，不处理同名冲突的优先级；
- 后端 `FlinkxJson` 按 `columns` 顺序生成 reader / writer 字段，无字段级来源优先级。

### 3.5 初步方向

- 在合表 / 多输入节点为每个来源增加**优先级**（或「主表」单选标志）；
- 同名字段按优先级取最高优先级来源的值；
- 冲突时是否允许「非空优先」作为兜底策略，作为可选项。

## 4. 需求四：前端配置里要有标志

### 4.1 目标

上述三项需求都要在数据集成前端节点配置中暴露对应标志，供用户配置。

### 4.2 建议的配置标志

| 需求 | 前端位置 | 新增标志 | 形态 |
| --- | --- | --- | --- |
| 来源字段 | 输入节点 `input/tableForm.vue` / `input/tableMerge.vue` | 「写入来源字段和写入时间」开关 | 开关 |
| 来源标识 | 合表输入 `input/tableMerge.vue` | 后端按每个源表名注入 `source_table` | 自动生成 |
| Upsert 唯一键 | 输出节点（已有「更新主键字段」） | 复用 `selectedColumns`，明细层强制 | 多选（已有） |
| Upsert 更新范围 | 输出节点「写入模式=增量更新」下 | 「更新列范围」：全列 / 指定列 | 单选 / 多选 |
| 主表优先级 | 合表输入 / 多输入节点 | 每个来源「主表」标志 或 优先级数值 | 单选 / 数字 |

### 4.3 现状对照

- `output/tableForm.vue` 已有「写入模式」（`writeModeType`）与「更新主键字段」（`selectedColumns`），可作为 Upsert 配置的落点；来源元数据由输入节点生成并在发布时继承到 writer；
- 合表节点、字段映射节点目前**无**来源 / 优先级标志，需新增。

### 4.4 关键约束

- 标志需随任务草稿保存（`taskParams`）并在编辑 / 详情回显；
- 复制任务、二次发布时必须同步这些标志（参考 `docs/flinkx-incremental-sync-fix-plan.md` 的复制重建经验）。

### 4.5 连续输出与多阶段合并

当前画布的基础组件是「输入节点 → 转换节点 → 输出节点」，且输入节点不能作为下游目标、输出节点不能继续连接下游。这个模型无法直接表达下面的分层链路：

```text
A 源表 ──> A 集成 ──> ODS_A ──┐
                              ├──> C 合并 ──> DWD_C
B 源表 ──> B 集成 ──> ODS_B ──┘
```

因此前端不再把 A、B、C 拆成独立的输入 / 输出组件来表达，而是增加一层**逻辑集成节点（Pipeline Node）**：

- 一个逻辑集成节点同时拥有 `inputs`、`transforms`、`output`；
- 普通同步节点的 `inputs` 只有一个来源；
- 合并节点的 `inputs` 可以有多个来源，并通过 `mergeConfig` 描述 `UNION_ALL` 或后续的 `JOIN`；
- 画布上的连线只表示**节点依赖**，不再表示 reader / writer 的端口连接；
- A、B、C 都是可作为上游和下游的逻辑节点，因而可以自然表达 A→C、B→C。

建议的草稿结构如下（字段名可在实现时按现有 `taskParams` 兼容映射）：

```json
{
  "pipelineNodes": [
    {
      "nodeId": "A_ODS",
      "nodeType": "INTEGRATION",
      "layer": "ODS",
      "inputs": [{ "kind": "TABLE", "table": "source_a" }],
      "transforms": [],
      "output": { "table": "ods_a" },
      "schemaMonitoring": { "enabled": true }
    },
    {
      "nodeId": "B_ODS",
      "nodeType": "INTEGRATION",
      "layer": "ODS",
      "inputs": [{ "kind": "TABLE", "table": "source_b" }],
      "transforms": [],
      "output": { "table": "ods_b" }
    },
    {
      "nodeId": "C_DWD",
      "nodeType": "MERGE",
      "layer": "DWD",
      "inputs": [
        { "kind": "NODE_OUTPUT", "refNodeId": "A_ODS", "alias": "a" },
        { "kind": "NODE_OUTPUT", "refNodeId": "B_ODS", "alias": "b" }
      ],
      "mergeConfig": { "type": "UNION_ALL" },
      "output": {
        "table": "dwd_c",
        "qualityConfig": { "enabled": true }
      }
    }
  ],
  "edges": [
    { "source": "A_ODS", "target": "C_DWD" },
    { "source": "B_ODS", "target": "C_DWD" }
  ]
}
```

其中：

1. 普通节点沿用现有输入表、转换、输出表配置；只是保存时封装为一个逻辑节点。
2. 合并节点的多输入只允许引用上游节点输出，不能绕过依赖直接引用不存在的中间结果。
3. `UNION_ALL` 继续复用现有 `tableMerge` 的结构相同表合并能力；`JOIN` 作为后续能力单独增加连接条件、主表和字段优先级配置。
4. 节点的来源元数据配置放在逻辑节点的输入侧，质量配置放在逻辑节点的输出侧；两者都不写入运行日志或原始业务字段之外的质量结果字段。
5. 逻辑节点保存前需要读取源字段，并保存 `columns` / `tableFields` / `targetColumns`；输出写入模式复用现有 `writeModeType`（全量、追加、增量更新）和 `selectedColumns`（更新主键）。
6. 当节点引用上游逻辑节点时，发布器自动继承上游目标数据源，并保留已有 `source_table`、自然键等来源字段；`write_time` 重新生成，表示当前层写入时间。
7. 连续输出会按上游实际已经落库的治理列继承可选字段；如果一个 `UNION_ALL` 合并节点的上游治理列集合不一致，发布前直接报错，避免运行时因分支字段不齐导致 SQL 失败。

这里不建议仅仅放开现有「输入节点不能作为目标、输出节点不能作为源」的校验。这样虽然能画出更多连线，但一个节点的 reader / writer 边界、字段传递范围和 FlinkX Job 切分都会变得不明确。应新增逻辑集成节点，旧的输入 / 转换 / 输出组件继续兼容已有任务。

#### 前端配置表现

画布只展示用户真正配置的**逻辑集成节点**，不展示发布器自动展开的 DS 运行节点。每个逻辑节点使用一个卡片表示，卡片内部固定包含「输入来源 →（可选转换）→ 输出目标」三个区域：

```text
┌──────────── A：普通集成 ────────────┐       ┌──────────── C：数据合并 ────────────┐
│ 输入：source_a                      │       │ 输入：A_ODS、B_ODS（多选）         │
│ 层级：ODS                            │ ───┐  │ 合并：UNION ALL                    │
│ 输出：ods_a                          │    ├─>│ 层级：DWD                           │
└─────────────────────────────────────┘ ───┘  │ 输出：dwd_c                         │
                                              └─────────────────────────────────────┘
┌──────────── B：普通集成 ────────────┐   ───┘
│ 输入：source_b；输出：ods_b          │
└─────────────────────────────────────┘
```

- 普通集成节点只能配置一个物理表输入，也可以通过「引用上游节点输出」把上游目标表作为本节点输入；因此同一个节点既是上游输出，又能继续作为下游输入。
- 合并节点不直接让用户填写中间表名，而是在「输入节点」多选框中选择 A、B 等逻辑节点；发布时再由后端把它们解析成 `ods_a`、`ods_b`。
- 画布连线和合并节点的多选输入同时保存：连线用于表达任务依赖，多选输入用于表达 FlinkX reader 的具体来源。删除连线时必须同步清除对应的上游引用，避免出现“画布已断开但发布仍依赖”的隐性配置。
- 前端禁止逻辑节点形成环；节点之间只允许形成 DAG。用户不需要配置元数据探查、质量检查的运行节点，仍只在节点卡片中打开开关并选择已有任务，发布器自动生成前置 / 后置 HTTP 节点。
- A、B、C 在前端仍是三个可编辑节点；发布时才展开为三个 DS FlinkX 数据节点，并根据依赖生成 `A → C`、`B → C` 两条 DS 关系。探查 / 质量节点属于运行展开结果，不回显为业务画布节点。

### 4.6 DolphinScheduler / FlinkX 发布展开

逻辑节点是前端配置单位，发布时展开为 DS 任务：

| 逻辑节点 | DS 数据任务 | FlinkX Job |
| --- | --- | --- |
| `A_ODS` | A 集成 | source_a → ods_a |
| `B_ODS` | B 集成 | source_b → ods_b |
| `C_DWD` | AB 合并 | ods_a + ods_b → dwd_c |

同时按配置自动插入探查 / 质量任务：

```text
元数据探查_A ──> A_ODS ──┐
                         ├──> C_DWD ──> 质量检查_C
元数据探查_B ──> B_ODS ──┘
```

- `schemaMonitoring.enabled=true`：复用现有元数据探查任务生成 DS 前置节点，先提交探查请求再运行对应集成任务；
  当前接口为异步触发，因此 `onDrift` 只有在后续增加结果轮询门禁后才能真正阻断任务。
- `qualityConfig.enabled=true`：复用现有质量检查任务生成 DS 后置节点，默认在目标表写入完成后执行；结果写入独立质量结果表。
- 当前质量检查接口是异步提交任务：HTTP 节点成功表示“已触发质量任务”，不等于质量规则已通过，因此不会自动阻断后续 DS 节点。若需要严格门禁，应新增同步执行/轮询结果节点，再按 `onFailure=FAIL` 阻断下游。
- 若未来需要“质量不通过则不提交正式表”，将 C 的 writer 改为临时表，展开为「写临时表 → 质量检查 → 合并 / 发布正式表」三段，不改变前端逻辑节点模型。

发布时的依赖关系直接由 `edges` 加上自动生成的探查 / 质量节点得到，前端不需要让用户手工画这些运行节点。

当前配置约定：

- `schemaMonitoring.taskId`：已有元数据探查任务 ID；发布器生成 HTTP 节点调用 `/cat/taskExecutor/runExecuteTask/{id}`；
- `output.qualityConfig.taskId`：已有质量检查任务 ID；发布器生成 HTTP 节点调用 `/quality/qualityTaskExecutor/runExecuteTask/{id}`；
- 前端配置会从现有元数据探查任务 / 质量检查任务列表加载可选项；历史草稿中已经保存但当前列表不可见的任务 ID 仍会保留并回显，避免编辑任务时丢配置；
- 开启元数据探查或质量检查后必须选择对应任务 ID；如果只打开开关但未绑定任务，发布前直接报错，
  不生成“看起来启用但实际未执行”的空 DS 节点；
- 运行监控、质量报告和探查结果均保留在各自任务/结果表中，不回写 ODS/DWD 业务表；
- `UNION_ALL` 合并节点发布前会把 `NODE_OUTPUT` 引用解析成上游节点的目标表名，再生成单个 FlinkX reader 的 `UNION ALL` SQL。
- `UNION_ALL` 发布前同时校验所有上游的业务字段集合和治理字段集合；字段不一致时直接阻止发布，避免运行时才发现分支结构不兼容。
- 目标表需要预先包含来源治理列（至少 `source_table`、`write_time`）；当前逻辑节点会把这些列加入 writer 映射，
  并在发布前通过数据源元数据接口校验，不在发布时隐式修改生产表结构。

## 5. 待确认问题

1. **来源字段命名与数量**：`data_source` / `source_system` / `source_table` / `etl_batch` / `load_time` 具体取几个、叫什么、什么类型？
2. **是否固定来源字段**：所有原始层表统一同一套来源列，还是每个任务可自定义列名？
3. **唯一键形态**：单列 / 复合 / 业务主键？主键是否允许为空？
4. **更新列范围**：整行覆盖，还是排除主键 / 来源列的指定列更新？
5. **主表优先级粒度**：表级（整个来源）还是字段级（每个同名字段单独指定主表）？
6. **空值策略**：主来源字段为空时，覆盖为 null 还是回退次优先级来源？
7. **是否启用时间戳比较**：`应用最新值` 策略是否需要（要求来源带 UTC 时间戳）？
8. **与 ingestion 统一**：明细层 Upsert 是否复用 ingestion 的 `key-columns` + `UPSERT` 口径，避免两套冲突策略？
9. **Doris 特殊性**：Doris 表模型（Unique / Aggregate / Duplicate Key）由谁约束？前端是否需要提示？

## 7. 验收标准（初拟）

- 原始层任意来源写入的记录，均可通过来源字段定位到源数据源 + 源表 + 任务 / 批次；
- 明细层同一任务重复执行，主键相同的记录不重复、被更新而非追加；
- 多来源同名字段时，按配置的主表 / 优先级取到预期来源的值；
- 上述配置均可在前端节点配置中设置、保存、回显，复制与二次发布后不丢失。
