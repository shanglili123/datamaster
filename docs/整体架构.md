# 整体架构

## 架构原则

数据源、数据探查是整个平台的核心基础。数据资产自动从元数据获取并作为未审核资产，数据服务与 AI 依赖数据资产对外提供能力；当数据资产数据缺失时，降级到数据探查元数据。

```text
        ┌─────────────────────────────┐
        │  数据服务 (datamaster-service) │   API 发布 / 转发 / SQL 查询
        │  AI 问数 (datamaster-ai)      │   自然语言取数 / 技能 / 分析
        └──────────────┬──────────────┘
                       │ 依赖（唯一入口：资产治理接口）
        ┌──────────────▼──────────────┐
        │  数据资产 (datamaster-assets) │   元数据扩展层：表/字段 + 空间授权 + 字段权限 + 审核
        └──────────────┬──────────────┘
                       │ 自动获取（未审核资产）+ table_id 关联
        ┌──────────────▼──────────────┐
        │  数据探查 (datamaster-metadata)│   元数据采集 / 库表字段 / 探查日志 / 质量探查
        └──────────────┬──────────────┘
        ┌──────────────▼──────────────┐
        │  数据源 (datasource)          │   各类数据库连接（MySQL/Doris/Oracle/...）
        └─────────────────────────────┘
```

## 分层职责

### 1. 数据源

各类数据库连接的登记与管理，是整个链路的数据访问基础。

- 资产侧登记：`AST_DATASOURCE`（datamaster-assets）
- 连接信息经 `datamaster-common-datasource-mgmt` 的 `IDatasourceApiService` 提供给查询链路
- 查询执行统一走公共工具 `datamaster-common-common` 的 `DataSourceFactory` + `DbQuery`（简单参数：dbType/ip/port/config + sql + 参数 + 分页）

### 2. 数据探查（核心基础）

负责发现数据结构，产出元数据，是资产的唯一数据来源。

- 探查任务：`CATALOG_TASK` / `CATALOG_TASK_INSTANCE`（调度采集）
- 元数据主表：`CATALOG_DB` / `CATALOG_TABLE` / `CATALOG_COLUMN`
- 探查日志：`CATALOG_TABLE_LOG` / `CATALOG_COLUMN_LOG` / `CATALOG_TABLE_COLUMN_REL_LOG`（每次探查快照）
- 质量探查：`QUALITY_TASK` / `QUALITY_LOG` / `QUALITY_TASK_OBJ`，通过 `CATALOG_TASK_QUALITY` 绑定到探查任务，采集成功后联动执行

### 3. 数据资产（元数据上的扩展层）

资产不是独立造数，而是在探查元数据之上扩展的登记、授权、审核实体。

- 自动获取元数据：探查产出的 `CATALOG_TABLE` 自动生成未审核资产，资产 `AST_ASSET` 通过 `table_id` 关联 `CATALOG_TABLE`，冗余表名/描述/数据量/字段量，`source=1` 表示数据发现来源。
- 字段继承与扩展：`AST_ASSET_COLUMN` 由 `CATALOG_COLUMN` 构造（`AssetsAssetColumnDO(CatalogColumnRespDTO)`），并在此基础上扩展标准数据元关联（`dataElemCodeId`）、敏感等级（`sensitiveLevelId`）、清洗/审计规则关联。
- 授权体系：`AST_ASSET_SPACE_REL`（空间级）、`AST_ASSET_COLUMN_SPACE_REL`（字段级）。
- 审核状态：自动生成的资产为未审核状态，审核通过后正式作为对外可用资产。
- 当前改造方向：资产收敛为纯数据资产（数据库表），不保留 API/GIS 等非数据资产类型。

### 4. 数据服务与 AI（依赖数据资产的消费层）

服务与 AI 不直接依赖探查原始元数据，统一依赖资产治理接口。

- 数据服务（datamaster-service）：`ApiMappingEngine` 执行链 = 取数据源连接 → 资产治理检查 → 拼 SQL → `DbQuery` 查询。
- AI 问数（datamaster-ai）：`AiAskDataServiceImpl` / `AiSkillServiceImpl` 在执行前同样调用资产治理接口。

### 5. 降级策略

当数据资产数据缺失（未找到资产或资产未审核）时，统一降级到数据探查元数据。

- 降级点在治理接口 `AssetsTableGovernanceApiServiceImpl.resolveTable`：
  - 命中资产 → `SOURCE_ASSET`（按空间/字段权限检查）
  - 未命中资产 → 回退到元数据采集 → `SOURCE_CATALOG`（`catalogTableApiService.getByDatasourceIdAndTableName`）
  - 两者皆无 → `SOURCE_NONE`
- 服务与 AI 都走同一个接口，保证降级行为一致。
- 降级开关：`fallbackToCatalog` 配置控制是否回退到元数据。

## 依赖方向

```text
datamaster-common（公共底座：数据源工具、数据源管理、基础工具）→ 无业务模块依赖
datamaster-metadata（数据探查）→ 依赖数据源、公共底座
datamaster-assets（数据资产）→ 依赖数据探查元数据（table_id / CatalogColumn）、公共底座
datamaster-service（数据服务）→ 依赖资产治理接口、数据源工具、公共底座
datamaster-ai（AI 问数）→ 依赖资产治理接口、元数据、数据服务能力
```

核心约束：

- 资产只读探查元数据并扩展，不反向依赖探查。
- 服务与 AI 只依赖资产治理接口，不直接操作资产表。
- 无资产时降级到元数据，保证查询链路可用性。
