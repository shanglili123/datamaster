# 整体规范化改造目标与方案

## 修改目标

本次改造目标是基于现有 DataMaster 系统，生成一套命名更规范、字段更清晰、重复逻辑更少、业务语义更统一的新系统实现。

系统整体架构、主要业务流程和当前 UI 风格保持不变，重点放在业务字段、数据库字段、接口参数、方法名称、注释、菜单权限和重复代码治理上。

核心目标：

1. 统一业务概念：业务语义中的 `Project/项目` 全部统一为 `Space/空间`。
2. 规范字段名称：字段、属性、方法、接口参数、数据库字段必须表达真实业务含义。
3. 数据库同步改造：表名和字段名一起改，不保留旧字段兼容。
4. 删除重复字段：同义字段只保留一个，例如 `description` 和 `remark` 默认保留 `description`。
5. 降低代码重复率：合并重复查询、重复保存、重复权限判断和废弃兼容逻辑。
6. 统一注释文案：Java 注释、`@Schema`、Excel 名称、前端 label、placeholder、校验提示保持一致。

## 怎么修改

### 1. 空间体系

统一替换规则：

```text
Project       -> Space
project       -> space
项目           -> 空间
projectId     -> spaceId
projectCode   -> spaceCode
projectName   -> spaceName
projectList   -> spaceList
PROJECT_ID    -> SPACE_ID
PROJECT_CODE  -> SPACE_CODE
project_id    -> space_id
project_code  -> space_code
```

数据库表名示例：

```text
TAX_PROJECT                  -> TAX_SPACE
TAX_PROJECT_USER_REL         -> TAX_SPACE_USER_REL
AST_DATASOURCE_PROJECT_REL   -> AST_DATASOURCE_SPACE_REL
AST_ASSET_PROJECT_REL        -> AST_ASSET_SPACE_REL
AST_ASSET_COLUMN_PROJECT_REL -> AST_ASSET_COLUMN_SPACE_REL
```

### 2. 数据源管理

数据源管理统一使用“数据源”概念：

```text
数据连接名称 -> 数据源名称
数据连接类型 -> 数据源类型
```

字段取舍：

- 保留 `description`，页面显示“描述”。
- 删除业务表单、VO、响应里的重复 `remark`。
- 前端不再展示、提交、维护“备注”。

### 3. 数据库迁移

数据库和代码同批上线：

- 直接 rename 表和字段。
- 不保留旧字段。
- 不写兼容视图。
- 不做双字段同步。
- 迁移前备份数据库。

当前脚本：

```text
sql/update_20260728_project_columns_to_space.sql
sql/update_20260728_space_menu_routes.sql
sql/update_20260728_quality_to_quality_inspection.sql
```

### 4. 接口和代码

所有本系统业务接口统一使用：

```java
private Long spaceId;
private String spaceCode;
private String spaceName;
private List<?> spaceList;
```

不再使用：

```java
private Long projectId;
private String projectCode;
private String projectName;
private List<?> projectList;
```

方法名同步改造：

```text
getProjectById        -> getSpaceById
getProjectCode        -> getSpaceCode
getProjectUserRelPage -> getSpaceUserRelPage
createProject         -> createSpace
updateProject         -> updateSpace
```

### 5. 权限和菜单

权限标识统一改为空间语义：

```text
tax:project:*         -> tax:space:*
col:project:role:*    -> col:space:role:*
projectUserRel        -> spaceUserRel
ProjectBaseManagement -> SpaceBaseManagement
```

系统权限字段同步改：

```text
system_role.project_id      -> system_role.space_id
system_role_menu.project_id -> system_role_menu.space_id
```

### 6. 模块推进顺序

建议顺序：

1. 空间主数据和空间成员。
2. 数据源管理。
3. 资产、字段权限、资产申请。
4. 目录、标准、标签、分类、规则。
5. 服务 API 和 AI 问数。
6. 采集、质量、ETL 中的空间字段。
7. 全局扫描和重复逻辑治理。

### 7. 目标模块边界划分

当前系统先按“清晰模块化单体”治理，不按微服务直接拆分。模块重整的目标是让业务边界更贴近数据治理和数据分析场景，减少历史模块之间的职责交叉。

目标边界如下：

```text
平台核心
  - 系统管理
  - 空间、组织、用户、角色、权限
  - 数据源管理
  - 监控运维
  - 数据标准
  - 类目、标签、主题域
  - 数据建模基础

数据探查
  - 元数据采集
  - 库表字段获取
  - 数据画像
  - 质量探查
  - 探查报告

数据资产
  - 资产目录
  - 资产登记
  - 资产归属
  - 资产申请
  - 字段权限
  - 资产发布

数据开发
  - SQL / Python / Shell / 存储过程任务
  - 任务编排
  - 调度发布
  - 任务实例
  - 执行日志
  - 结果数据集

数据服务
  - API 发布
  - 参数配置
  - SQL 服务
  - 服务鉴权
  - 限流
  - 调用日志
  - 服务下线
  - 服务市场

AI 分析
  - AI 问数
  - Skill
  - 分析方案
  - 转数据开发任务
  - 报告生成
```

依赖原则：

- 平台核心是底座，其他模块都可以依赖。
- 数据探查依赖数据源、标准、类目和权限，负责发现数据结构、画像和质量问题。
- 数据资产依赖数据探查结果和平台核心，负责把数据登记成可管理、可授权、可发布的资产。
- 数据开发依赖数据源、资产、标准、类目、权限和调度能力，负责加工和产出结果数据。
- 数据服务依赖资产和数据开发结果，负责把数据能力包装成可调用 API。
- AI 分析依赖资产、探查、标准、类目、质量结果、数据开发任务、结果数据集和报告模板，负责生成分析方案并沉淀为系统任务。

边界要求：

- 数据资产和数据开发强关联，但不合并为同一模块。
- 数据服务独立成服务消费层，不并入资产或数据开发。
- AI 问数不塞进资产或数据开发，作为上层智能分析能力独立治理。
- 元数据获取和质量探查可以按“数据探查”方向收敛，减少重复的数据源、表字段和探查报告逻辑。

## 什么不修改

1. 不换 UI 框架
   - 当前 UI 框架和视觉风格不改。
   - 不强制改 Ant Design。

2. 不重做主流程
   - 数据源、空间、资产、目录、标准、采集、质量等主业务流程保持不变。

3. 不直接拆微服务
   - 当前阶段按模块化单体治理项目结构和业务边界。
   - 不把现有 `api/biz` 模块直接等同于微服务。
   - 不新增服务注册、网关、远程调用或独立数据库拆分。
   - 后续如需微服务化，必须先完成模块边界、表归属、接口契约和调用链路治理。

4. 不重写 ETL 参数包装转换
   - ETL 任务参数包装和转换为 ETL 的核心逻辑不主动重写。
   - 保留现有 ChunJun/FlinkX 主链路。
   - 旧独立执行模块已按最新要求删除，不再作为保留范围。

5. 不强改第三方协议
   - DolphinScheduler 外部 API 中本身叫 `projectCode`、`projects` 的地方，如果是第三方协议要求，可以保留。
   - 不能把第三方 API 参数误改成本系统字段。
   - AI 问数模块保持现有命名，不做 Project→Space 改造。

6. 不改生成产物
   - 不修改 `target`、`dist`、`${project.build.directory}` 等生成目录。

7. 不做旧系统兼容
   - 不兼容旧数据库字段。
   - 不兼容旧接口字段。
   - 不兼容旧菜单路由。
   - 不兼容旧权限标识。

## 风险说明

- 这是一次不兼容改造，数据库脚本和代码必须一起发布。
- 只改代码不改数据库会导致 SQL 报字段或表不存在。
- 只改数据库不发代码会导致旧 SQL 不可用。
- 外部系统如果仍调用旧接口字段，需要同步调整。
- 全局替换时必须区分本系统业务字段和第三方协议字段，避免误改 DolphinScheduler 等外部接口。
