# 本体动作可靠触发 V1 实施方案

> 实施状态：代码已按本文方案落地；数据库需执行
> `sql/update_20260905_ont_action_stage1_runtime.sql` 后启用。

## 0. Palantir 口径边界

Palantir Ontology 公开模型中没有一个与 Object Type、Link Type、Action Type 并列的通用 `Decision` 原语。“决策闭环”通常由对象、函数/规则、Action、应用交互、自动化和人工确认组合形成。

因此本文设计的是 **DataMaster 自有可靠动作运行时**：

- Action 是受权限、条件和审计约束的业务命令；
- 前置条件决定动作在当前业务状态下是否允许执行；
- Approval 仅用于一次可选的人工确认，不承载规则判定依据；
- Worker 负责获准后的可靠领取与执行；
- Workflow 才负责多个 Action 的串行、条件、并行和汇聚；
- Proposal/DecisionRecord 如后续需要，是 DataMaster 的业务扩展，不冒充 Palantir 官方原语。

## 1. 本次目标

本次只完成 Workflow 之前的可靠单动作触发底座：

```text
数据到达 / API / 人工提交
    → 创建持久 ActionExecution
    → 前置条件检查
    → 按动作执行模式：直接执行 / 等待一次人工确认
    → AUTO_EXECUTE=true
    → 数据库 Worker 抢占
    → 执行动作
    → 记录结果
```

不在本次引入 Action Workflow、条件节点、并行节点和补偿编排。这些能力以后复用本次形成的可靠执行底座。

## 2. 当前问题

1. 数据到达触发只调用 `submitExecution`，免审批后停在 `APPROVED`，不会自动执行。
2. 接收模块收到 Kafka 数据后，通过 HTTP 回调，但没有传递 `inputParams`、对象主键和事件编号。
3. 动作执行依赖用户或前端再次调用 `/execution/run/{id}`。
4. 只有瞬时 `LOCK_TIME` 并发锁，没有后台 Worker 和进程崩溃后的锁异常标记。
5. 动作、函数虽然有版本字段，但定义更新时没有递增版本。
6. `object.<property>` 解析顺序错误，联合主键只取第一个值。
7. 幂等键后端已支持，但现有数据触发入口没有生成幂等键。

## 3. 实现选择

### 3.1 持久队列

V1 直接使用 `ONT_ACTION_EXECUTION` 作为持久执行队列，不新增消息中间件：

- `APPROVED + AUTO_EXECUTE=true`：等待 Worker 执行；
- `RUNNING`：已被一个执行线程抢占；
- `EXECUTED / FAILED / RECONCILIATION_REQUIRED`：终态或需人工处理。

### 3.2 调度方式

复用仓库已有能力：

- `@EnableScheduling`；
- `threadPoolTaskExecutor`；
- PostgreSQL/MyBatis 条件更新完成 CAS 抢占。

Worker 先查询候选记录，实际执行前以：

```text
ID + STATUS=APPROVED + LOCK_TIME IS NULL
```

做条件更新。多实例同时扫描也只有一个实例能抢占成功。

### 3.3 数据到达触发

`datamaster-ingestion` 已依赖 `datamaster-ontology-interface`，因此聚合部署时直接调用接口，不再绕本机 HTTP：

```text
IngestionKafkaConsumer
    → IActionTriggerApiService
    → ActionExecutionService.submitByTrigger
```

独立部署时保留 HTTP 回退，并通过请求头传递共享密钥。

Kafka 事件幂等键：

```text
topic:partition:offset:actionId
```

### 3.4 触发方式与执行模式分离

- 触发方式决定动作如何被提交：人工点击或数据到达；
- 执行模式决定提交后是否需要人介入：直接执行或人工确认后执行；
- 人工点击也可以直接执行：创建执行记录后设置 `AUTO_EXECUTE=true`，由 Worker 执行；
- 需要人工确认的动作最多一名确认人、一次确认，意见可选；确认通过后设置 `AUTO_EXECUTE=true`；
- 数据到达触发固定为直接执行，不进入人工确认；
- 现有 `/execution/run/{id}` 只保留为旧执行记录兼容入口。

## 4. 数据结构调整

`ONT_ACTION_EXECUTION` 新增：

```text
AUTO_EXECUTE
TRIGGER_TYPE
TRIGGER_REF
EVENT_ID
MAX_ATTEMPTS
NEXT_RUN_TIME
LOCK_OWNER
```

状态新增：

```text
RUNNING
RECONCILIATION_REQUIRED
```

`RUNNING` 超过锁超时时间不自动重放写动作，而是进入 `RECONCILIATION_REQUIRED`，避免目标库已经成功但管理库未记录时重复写入。

## 6. 安全与失败策略

1. 数据事件必须携带稳定 `eventId`。
2. 聚合部署使用 Java 接口调用；HTTP 回退必须配置共享密钥。
3. Worker 不依赖登录线程的 `SecurityContext`，使用执行记录中冻结的空间和发起上下文。
4. 执行失败不盲目自动重试写动作。
5. 执行线程失联后标记 `RECONCILIATION_REQUIRED`，由后续对账机制判断目标状态。
6. 联合主键必须完整参与对象状态查询，不允许只取第一列。

## 8. 已落地实现

### 8.1 触发与幂等

- Kafka 消费成功后生成 `topic:partition:offset` 事件编号；
- 对每个匹配动作生成 `topic:partition:offset:actionId` 幂等键；
- 聚合部署优先通过 `IActionTriggerApiService` 进程内调用；
- 独立部署保留 HTTP JSON 回调，并要求共享密钥请求头；
- 数据事件载荷、完整对象主键、事件编号写入执行记录。
- 动作在 SQL 生成、权限或参数校验阶段失败时，也落一条 `TRIGGER_SUBMIT_ERROR` 执行记录，避免事件静默丢失。

### 8.2 自动执行

- `AUTO_EXECUTE` 表示“本次执行现在无需人工确认，可由 Worker 直接执行”，不表示触发来源；
- 人工点击提交的直接执行动作也设置 `AUTO_EXECUTE=true`；
- 人工确认模式提交后进入 `PENDING_APPROVAL`，只允许一次确认，意见可选；
- 确认通过后设置 `APPROVED + AUTO_EXECUTE=true`，由 Worker 自动继续；
- 数据到达触发固定设置 `AUTO_EXECUTE=true`，不进入人工确认；
- 所有路径都先创建并持续更新 `ONT_ACTION_EXECUTION`，直接执行不等于不记录过程。

### 8.3 执行安全

- CAS 将 `APPROVED → RUNNING`，同时写 `LOCK_TIME / LOCK_OWNER / ATTEMPT_NO`；
- `RUNNING` 在访问业务库前单独持久化，不被管理库长事务包住；
- 业务执行完成后写入 `EXECUTED / FAILED` 和统一 `RESULT_CONTEXT`；
- 锁超时转为 `RECONCILIATION_REQUIRED`，不自动重放外部写操作；
- 动作和函数更新时版本号递增，执行前复核冻结版本与函数哈希。

### 8.4 对象条件

- 修复 `object.<property>` 被错误判为缺少属性名的问题；
- 单主键兼容标量和 JSON；
- 联合主键查询必须包含全部主键列；
- 关系导航先用完整对象主键定位源行并读取 `sourceColumn`，再按 `targetColumn` 查询目标对象；语义与对象浏览器一致。

### 8.5 前端运行视图

- 动作列表新增“触发方式”，直接区分人工触发和数据到达触发，并展示 `triggerRef`；
- 动作新增/编辑弹窗使用“人工触发 / 数据到达”显式选择，不再依靠是否填写输入框来隐式判断；
- 前端分别配置“触发方式”和“执行模式”，人工点击同样可以选择直接执行；
- 每个动作最多配置一名人工确认人；意见可选，确认结论与过程永久留痕；
- 数据到达模式固定直接执行，不提供人工确认配置；
- 执行记录展示触发来源、事件 ID、自动执行标识、尝试次数和错误码；
- `APPROVED + AUTO_EXECUTE=true` 或 `RUNNING` 的记录会在页面自动刷新，直到进入终态；
- 执行详情展示幂等键、锁持有者、锁时间、统一执行上下文以及错误信息；
- `RECONCILIATION_REQUIRED` 使用显著告警，提示先核对目标系统，不能直接重放写动作。

### 8.6 执行前置检查

动作的 `SUBMISSION_CRITERIA` 在界面上作为“执行前置检查”配置，支持：

- 当前对象属性：`object.<propertyCode>`；
- 关联对象属性：`object.<relationCode>.<propertyCode>`；
- 动作入参：`param.<name>`；
- 对象主键、当前用户和当前时间等运行上下文；
- `eq/ne/gt/ge/lt/le/contains/in` 运算符以及 AND/OR 组合。

关联属性的标量比较只开放一对一、多对一关系。一对多、多对多必须先在本体中定义数量、总量等聚合属性，不能用 `LIMIT 1` 随机取一条记录参与业务决策。

条件会执行两次：

1. 动作提交时检查，失败则不进入审批或自动执行队列；
2. 动作真正执行前，使用最新对象状态再次检查，失败则写入 `FAILED + PRECONDITION_FAILED`，且不产生业务副作用。

例如订单发货动作绑定“订单”概念，订单通过 `inventory` 关系关联“库存”概念，可配置：

```text
关联对象 → inventory → quantity → 大于 → 0
```

对应表达式为：

```json
{"logic":"AND","conditions":[{"field":"object.inventory.quantity","op":"gt","value":"0"}]}
```

注意：执行前检查只能防止使用明显过期的状态，不能单独解决并发超卖。库存扣减必须由库存系统使用条件更新、库存预占或带版本号的乐观锁原子完成，例如 `UPDATE inventory SET quantity = quantity - 1 WHERE id = ? AND quantity > 0`，并以影响行数为 1 作为成功依据。

## 9. 配置

```yaml
datamaster:
  ontology:
    action-trigger:
      # 仅独立部署 HTTP 回调需要；服务端与 ingestion 配置必须一致
      secret: ${DATAMASTER_ACTION_TRIGGER_SECRET:}
    action-execution:
      worker-enabled: true
      worker-delay-ms: 1000
      batch-size: 20
      lock-timeout-ms: 600000
  ingestion:
    decision-trigger:
      enabled: true
      # 聚合部署走进程内接口，不要求 base-url；独立部署才填写
      base-url: ${DATAMASTER_SERVER_URL:}
      path: /ont/action/trigger/data-arrival
      secret: ${DATAMASTER_ACTION_TRIGGER_SECRET:}
```
