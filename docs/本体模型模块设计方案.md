# 本体模型模块设计方案

## 1. 概述

### 1.1 目标

在 DataMaster 中新增 **本体模型（Ontology Model）** 模块，实现类似 Palantir Foundry 的虚拟本体能力：

- 定义语义层：概念（Concept）、属性（Property）、关系（Relation）
- 绑定物理层：概念 -> 表，属性 -> 字段，关系 -> 关联字段
- 声明式操作：对本体实例的增删改查自动翻译为 SQL
- 执行引擎：SQL 预览 -> 审核 -> 提交执行 -> 结果展示
- 外部通知：HTTP 回调、邮件、DolphinScheduler 通知
- 函数逻辑：支持 TypeScript / Python 自定义处理
- 本体模型可视化：图谱展示（AntV X6）

### 1.2 核心理念

与 Palantir 一致，本体是**虚拟语义层**，不是物理图数据库。数据留在源端，本体定义概念/关系/属性的映射关系，查询时动态翻译为源端 SQL。

```
本体定义（概念 / 关系 / 属性）
    | 映射
多源异构表（Oracle / MySQL / PostgreSQL / Hive ...）
    | 动态翻译
源端 SQL 执行 -> 结果聚合
```

### 1.3 实施阶段

| 阶段 | 内容 | 依赖 |
|------|------|------|
| 第一步 | 本体 CRUD：概念、属性、关系的创建和管理 | 无 |
| 第二步 | 本体绑定：概念绑表、属性绑字段、关系绑关联字段 | 第一步 |
| 第三步 | 声明式动作 + SQL 翻译引擎 + 预览审核 + 差异展示 | 第二步 |
| 第四步 | 外部通知：HTTP 回调、邮件、DS 通知 | 第三步 |
| 第五步 | 函数逻辑：TypeScript / Python 自定义处理 | 第三步 |
| 第六步 | 本体模型可视化：图谱展示（AntV X6） | 第一步 |

> 第三步的提交需要审批，第五步的函数自动执行需要审批。

**技术约定（沿用现有模式）：**
- Controller: `@Tag` + `@RestController` + `@RequestMapping("/ontology/...")`，extends `BaseController`，返回 `CommonResult<T>`
- Service: `IService<DO>` 接口 + `ServiceImpl extends ServiceImpl<Mapper, DO>`
- Mapper: `extends BaseMapperX<DO>`，使用 `MPJLambdaWrapperX` 构建查询
- DO: `@Data` + `@TableName("ONT_...")` + extends `BaseEntity`（雪花 ID + 审计字段）
- Convert: MapStruct `@Mapper` + `INSTANCE = Mappers.getMapper(...)`
- 表名前缀：`ONT_`

## 4. 第三步：声明式动作 + SQL 翻译引擎

### 4.1 核心概念

**本体动作（Ontology Action）**：对本体实例的声明式操作，不直接写 SQL，描述"对哪个概念做什么"。

| 动作 | 说明 | 示例 |
|------|------|------|
| CREATE | 创建概念实例 | 创建一个"客户"实例 |
| UPDATE | 更新概念实例属性值 | 修改客户"张三"的手机号 |
| DELETE | 删除概念实例 | 删除客户"张三" |
| QUERY | 查询概念实例 | 查询所有 VIP 客户 |

### 4.2 数据模型

#### 4.2.1 动作定义（Action）

| 字段 | 类型 | 说明 |
|------|------|------|
| id | bigint | 主键 |
| ontology_id | bigint | 所属本体 |
| name | varchar(100) | 动作名称 |
| action_type | varchar(20) | CREATE / UPDATE / DELETE / QUERY |
| concept_id | bigint | 目标概念 |
| description | text | 描述 |
| param_config | text | 执行参数配置(JSON数组)：目标属性选择 + 目标值配置 |
| ... audit fields ... | | |

**表名：`ONT_ACTION`**

> **实施状态（2026-08）**：`PARAM_CONFIG` 列已落地（迁移脚本 `sql/update_20260824_ont_action_param_config.sql`）。三种目标值模式：
> - `direct`：固定字面值，生成 SQL 时正常加引号转义
> - `placeholder`：引用执行入参，模板形如 `${newStatus}`，提交执行时由用户填写
> - `expression`：原生 SQL 表达式（如 `CASE WHEN level='VIP' THEN 2 ELSE 1 END`），拼装时不加引号
>
> 配置样例：`[{"propertyCode":"status","valueMode":"direct","valueTemplate":"已审核","required":true}]`。
> 前端在动作新建/编辑对话框通过「目标属性」多选 + 每属性的取值模式和必填标记生成该 JSON；
> 提交执行对话框据此动态渲染表单（placeholder 型渲染输入框，direct/expression 型只读展示），
> 未配置 `param_config` 的旧动作保持手工 JSON 入参兼容。

### 4.3 SQL 翻译引擎

```
本体动作输入
    |
解析动作类型 + 目标概念
    |
查找概念绑定的表（ONT_CONCEPT_TABLE）
    |
查找属性绑定的字段（ONT_PROPERTY_COLUMN）
    |
查找关系绑定的关联字段（ONT_RELATION_COLUMN）
    |
翻译为目标数据源的 SQL（考虑方言差异）
    |
返回 SQL + 预览结果（不执行）
```

核心类设计：

```
service/ontology/impl/
  OntologyActionService.java      # 动作执行入口
  SqlTranslationEngine.java       # SQL 翻译引擎
  DialectResolver.java            # 数据源方言解析
  ActionPreviewService.java       # 预览服务（调用 DbQuery.queryByPage）
```

> **实际实现与设计差异（2026-08）**：
> - 动作执行入口为 `ActionExecutionServiceImpl`，SQL 生成、预演、快照、执行在同一服务内完成，未单独拆分 SqlTranslationEngine/DialectResolver。
> - 数据源路由按 `ONT_CONCEPT_TABLE.DATASOURCE_ID` 经 `IDatasourceApiService` 解析注册数据源，再由 `DataSourceFactory.createDbQuery()` 按方言构建 `DbQuery` 连接（支持 MySQL/Oracle/PG/达梦等），不依赖平台主库 JdbcTemplate。
> - SQL 拼装基于属性语义名 → 物理列映射（`ONT_PROPERTY_COLUMN` + `ONT_PROPERTY`），值统一经转义渲染；仅 `expression` 模式的目标值原样输出。
> - 字段权限：提交执行前按概念绑定物理表的 `DATASOURCE_ID + TABLE_NAME` 定位注册资产，复用资产治理跨模块 API `IAssetsTableGovernanceApiService.checkTableAccess()` 完成表级（`AST_ASSET_SPACE_REL`，含审批放行回退）与字段级（`AST_ASSET_COLUMN_SPACE_REL` 允许列交集）校验，入口标识 `ONTOLOGY_ACTION`。空间上下文由前端拦截器自动注入请求体（`spaceId`/`spaceCode`），`ExecutionSubmitReqVO` 已声明对应字段接收。

**SQL 翻译示例 - QUERY：**

```json
// 输入
{
  "actionType": "QUERY",
  "conceptCode": "customer",
  "filters": [
    { "propertyCode": "level", "operator": "=", "value": "VIP" }
  ],
  "selectProperties": ["name", "phone"]
}

// 输出 SQL
SELECT t1."NAME" AS "name", t1."PHONE" AS "phone"
FROM "CUSTOMER" t1
WHERE t1."LEVEL" = 'VIP'
```

**关系 JOIN 翻译：**

```json
// 输入：查询所有订单及其客户姓名
{
  "actionType": "QUERY",
  "conceptCode": "order",
  "selectProperties": ["orderId", "amount"],
  "includeRelations": ["customer"]
}

// 输出 SQL
SELECT t1."ORDER_ID" AS "orderId", t1."AMOUNT" AS "amount",
       t2."NAME" AS "customer.name"
FROM "ORDER" t1
LEFT JOIN "CUSTOMER" t2 ON t1."CUSTOMER_ID" = t2."ID"
```

**UPDATE 翻译：**

```json
// 输入：修改客户张三的手机号
{
  "actionType": "UPDATE",
  "conceptCode": "customer",
  "filters": [
    { "propertyCode": "id", "operator": "=", "value": 1001 }
  ],
  "updates": {
    "phone": "13900002222"
  }
}

// 输出 SQL
UPDATE "CUSTOMER" SET "PHONE" = '13900002222' WHERE "ID" = 1001
```

### 4.4 审核流程

```
用户执行动作 -> 生成 SQL + 预览结果
    |
状态：DRAFT
    |
用户提交审核 -> 状态：PENDING_APPROVAL
    |
审批人审核
    |-- 通过 -> 状态：APPROVED -> 执行 SQL -> 状态：EXECUTED
    |-- 拒绝 -> 状态：REJECTED（附审批意见）
```

**复用现有审核模式（AST_ASSET_APPLY）：**
- 状态字符串常量管理
- 审批人通过 update 接口更新状态
- 复用 `ISysMessageService.send(templateId, ...)` 发送审批通知（新建模板 ID）
- 前端复用审批对话框模式（通过/拒绝 + 审批理由）
- `@Log` 注解记录审批操作到 `SysOperLog`

**两阶段安全语义（已实现并修复）：**
- 提交阶段仅生成 SQL 并预检，业务库不发生任何变更：SELECT 直接查询返回行；UPDATE/DELETE 在独立事务内执行后立即回滚，只返回影响行数作为预览。
- 真正落库只发生在审批通过后的 execute 阶段；修改前数据（before_data）快照取自提交时刻，保证审批人审阅的即是被修改前的真实数据。
- 执行失败时记录置为 FAILED 并保存 error_message，不影响业务数据。

### 4.5 差异展示

SQL 执行前展示修改结果预览：

```
+-------------------------------------------+
| 修改预览                                  |
+-------------------------------------------+
| 操作类型：更新                            |
| 目标表：CUSTOMER                          |
| 条件：ID = 1001                           |
+-------------------------------------------+
| 修改前           | 修改后                  |
| 张三             | 张三                   |
| 13800001111      | 13900002222  <-- 修改  |
| VIP              | VIP                    |
+-------------------------------------------+
| [预览 SQL]  [提交审核]  [取消]            |
+-------------------------------------------+
```

预览实现：
- UPDATE/DELETE：先执行 SELECT 查询当前值作为 `before_data`
- CREATE：展示将要插入的完整数据
- QUERY：直接展示查询结果
- 复用 `DbQuery.queryByPage` 和 `AssetsDatasourceService.executeSqlQuery` 执行预览查询

## 6. 第五步：函数逻辑

### 6.1 概念

支持用户编写自定义函数来扩展本体动作的处理逻辑。函数在动作执行前后运行，可以做数据转换、校验、聚合等。

| 函数类型 | 说明 | 运行环境 |
|----------|------|----------|
| TypeScript | 前端熟悉，适合数据转换和校验 | 后端 Node.js / GraalJS 引擎 |
| Python | 数据分析、ML 推理 | 后端 GraalPython / Jython / 独立进程 |

### 6.2 数据模型

#### 6.2.1 函数定义（Function）

| 字段 | 类型 | 说明 |
|------|------|------|
| id | bigint | 主键 |
| ontology_id | bigint | 所属本体 |
| name | varchar(100) | 函数名称 |
| code | varchar(100) | 函数编码 |
| lang | varchar(10) | TYPESCRIPT / PYTHON |
| func_type | varchar(20) | PRE_HOOK / POST_HOOK / TRANSFORM / VALIDATOR |
| body | text | 函数代码体 |
| description | text | 描述 |
| enabled | boolean | 是否启用 |
| needs_approval | boolean | 是否需要审批（自动执行的函数必须为 true） |
| ... audit fields ... | | |

**表名：`ONT_FUNCTION`**

#### 6.2.2 函数执行记录（Function Execution）

| 字段 | 类型 | 说明 |
|------|------|------|
| id | bigint | 主键 |
| function_id | bigint | 函数 ID |
| execution_id | bigint | 关联的动作执行 ID |
| input | jsonb | 输入参数 |
| output | jsonb | 输出结果 |
| status | varchar(20) | PENDING_APPROVAL/APPROVED/REJECTED/SUCCESS/FAILED |
| approval_reason | text | 审批意见 |
| error_message | text | 错误信息 |
| duration_ms | bigint | 执行耗时 |
| ... audit fields ... | | |

**表名：`ONT_FUNCTION_EXECUTION`**

### 6.3 执行流程

```
动作触发
    |
PRE_HOOK 函数执行（如果有）
    |-- 需要审批 -> 状态 PENDING_APPROVAL -> 审批通过 -> 继续
    |-- 不需要审批 -> 直接执行
    |
SQL 翻译 + 执行
    |
POST_HOOK 函数执行（如果有）
    |-- 同上审批流程
    |
TRANSFORM / VALIDATOR 函数（数据转换/校验）
    |
完成
```

### 6.4 TypeScript 执行引擎

推荐方案：**GraalJS**（GraalVM 内置 JavaScript 引擎）

```java
// 方案一：GraalJS（推荐，与 JVM 集成，性能好）
try (Context context = Context.create("js")) {
    context.getBindings("js").putMember("input", inputData);
    context.getBindings("js").putMember("db", dbHelper);
    Value result = context.eval("js", functionBody);
}

// 方案二：独立 Node.js 进程调用（隔离性好，但部署复杂）
ProcessBuilder pb = new ProcessBuilder("node", scriptPath);
```

### 6.5 Python 执行引擎

推荐方案：**独立进程 + JSON 通信**

```java
// GraalPython 在 Java 8 不可用，使用独立进程方案
ProcessBuilder pb = new ProcessBuilder(
    "python3", scriptPath,
    "--input", inputFile.getAbsolutePath(),
    "--output", outputFile.getAbsolutePath()
);
```

函数代码中可使用的内置对象：
- `input`：输入参数（JSON 自动反序列化）
- `db`：数据库访问 helper（SELECT 查询，不直接执行写操作）
- `log`：日志输出
- `result`：返回结果赋值

### 6.6 审批机制

- `needs_approval = true` 的函数在执行前需要审批
- 自动执行的函数（POST_HOOK 等）**必须**设置 `needs_approval = true`
- 审批流程复用第三步的 `ONT_ACTION_EXECUTION` 审核模式
- 审批人可在审批前查看函数代码和预期输入/输出

### 6.7 前端

- 在本体管理页增加「函数」Tab
- 代码编辑器：集成 Monaco Editor（项目已有依赖）或 CodeMirror
- 支持 TypeScript / Python 语法高亮
- 函数测试面板：输入测试数据 -> 执行 -> 查看输出

## 7. 第六步：本体模型可视化

### 7.1 目标

以交互式图谱形式展示本体模型，直观呈现概念、属性、关系之间的结构。

### 7.2 技术选型

### 7.5 节点设计

```

+-------------------------------+

+-------------------------------+
```

节点宽度自适应，显示前 N 个属性（可展开全部）。

### 7.6 边设计

- 实线箭头：one_to_one / many_to_one
- 虚线箭头：one_to_many / many_to_many
- 边标签：关系名称

### 7.7 交互功能
