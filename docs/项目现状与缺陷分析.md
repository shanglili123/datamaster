# 项目现状与缺陷分析

更新时间：2026-10-14

本文按当前工作区代码、Maven 聚合配置、前端 `package.json`、部署脚本和离线 SQL 包盘点，不把历史方案文档当作已实现功能。

## 一、当前基线

- 后端是 Java 8、Spring Boot 2.5.15 的 Maven 多模块工程，根 `pom.xml` 当前聚合 13 个顶层模块；公共模块内部还有多个子模块。
- 后端启动入口为 `datamaster-server/src/main/java/com/datamaster/server/DataMasterApplication.java`，默认服务端口为 8989。
- 前端为 Vue 3 + Vite 5.3.2，UI 组件以 Ant Design Vue 4.2.6 为主；仓库中仍有少量迁移残留，需要继续以构建和页面回归确认。
- 主部署采用 Bash + SSH/SCP + 单容器 `docker run`，不使用 Docker Compose；ingestion 的 Kafka/Doris 是独立部署目录，默认关闭。
- Neo4j 血缘、Kafka/Doris ingestion、DB-GPT/模型能力均是按开关或场景启用的可选能力。

本轮功能修复已完成：Kafka 消费改为业务处理成功后手动提交 offset；增加可配置失败重试、退避、持久化重试次数、租约续期、死信 topic 以及死信查询/单条和批量人工重放接口；增加 `/ingestion/metrics` 运行指标接口和 `/ingestion/runtime` 实际消费者状态接口；`/ingestion/config` 改为脱敏配置摘要；死信重放限制为当前 ingestion 已配置的源 topic；增加动态目标表白名单、必填字段、Schema 版本、表名和字段名安全校验；复用 `INGESTION_LOG` 按 `topic + partition + offset` 跳过已成功处理事件，并通过 `INGESTION_EVENT` 租约限制跨实例并发处理；默认部署增量迁移 `sql/update_20261012_ingestion_reliability.sql` 同时创建两张表及索引；Agent 取消增加后台阶段检查、防止异步状态覆盖，并可向正在执行的元数据探查任务发出取消请求；ingestion 增加 `__op=DELETE`/`__operation=DELETE`/`__eventType=DELETE` 的按主键删除处理；修复 ingestion 对公共 `DbQuery.addTableData/updateTableData` 空实现的依赖，改为参数化 JDBC 实际落库；人工编辑仲裁增加数据源、空间维度过滤并兼容多目标表记录；UPSERT 改用 Doris 原生 `ON DUPLICATE KEY UPDATE`。仍需在实际 Doris Unique/Duplicate Key 表模型上联调确认语法和更新语义，以及核查历史执行记录的数据源字段回填策略。

本轮新增：数据资产操作申请增加 `DRAFT → PENDING_APPROVAL → APPROVED/REJECTED → EXECUTING → EXECUTED/FAILED` 状态流转、审批意见、审批人和执行结果；审批通过后执行会复用已有资产操作日志服务，避免绕过既有数据源和字段校验；前端申请 API 路径已与后端统一，并新增提交、审批、驳回、执行方法。部署脚本支持逗号分隔的多个应用增量 SQL，默认同时执行 ingestion 可靠性迁移和资产申请状态迁移。ingestion 的配置、运行态、指标和死信接口已增加查询/重放权限注解，死信重放写入操作审计日志。

本轮继续补齐了两个业务入口：新增资产操作申请管理页和 Ingestion 管理控制台，并实现 Workflow Runtime V2。Workflow 现在可以对已发布且启用的动作 DAG 手动或异步启动，支持基于对象状态、输入参数、上游步骤输出和运行上下文的结构化分支，支持可恢复的并行拆分/汇聚（当前逐分支执行，不是多线程同时执行）、持久化运行实例和节点步骤，记录底层动作执行结果，支持待审批状态、失败状态、续跑和取消；动作节点失败可按 `retryPolicy` 自动重试并记录每次尝试。节点 `timeoutMs` 已由 Workflow Worker 监控，超时会把底层动作和运行实例转为 `RECONCILIATION_REQUIRED`，停止自动重放并要求人工对账。失败或需人工对账的运行现在可以按已执行步骤逆序人工发起补偿计划；补偿动作必须属于同一本体并配置人工审批，只会进入现有动作审批/执行链，不会自动执行或把原 Workflow 伪装成成功。

Workflow 步骤现在会把 `workflowRunId`、`workflowStepId` 和上游执行记录 ID 写入底层动作执行记录，运行记录页面支持查看步骤、续跑和取消；触发事件 ID 也会进入运行上下文，便于条件判断和审计关联。启动请求支持 Workflow 级 `idempotencyKey`，数据库使用 `(workflow_id, idempotency_key)` 唯一索引阻止并发重复创建；`async=true` 时由持久化 Workflow Worker 领取 `QUEUED` 运行，避免长动作占用 HTTP 请求线程。配置 `triggerRef` 的已发布且启用 Workflow 会随受信任的数据到达事件自动异步入队，并按 `eventId + workflow` 幂等；工作站现已增加统一运行监控入口和 `GET /ont/workflow/monitor` 接口，按当前用户可见 Workflow 汇总状态并展示最近运行样本；失败和 `RECONCILIATION_REQUIRED` 状态会通过站内消息通知运行发起人，通知迁移为 `sql/update_20261014_workflow_alert_template.sql`。

Workflow Worker 现在会持续刷新本实例执行中运行的数据库心跳；服务崩溃或实例丢失后，超过 `WORKFLOW_WORKER_STALE_TIMEOUT_MS` 的 `RUNNING` 记录会重新进入 `QUEUED`。恢复后的动作提交继续使用 Workflow 节点幂等键，底层执行记录若进入需对账状态则停止自动重放。运行详情、续跑、取消、定义列表和定义编辑还会按本体所属空间做成员校验，避免仅凭运行 ID 或空本体分页请求越权操作。

Workflow 补偿当前属于“人工计划”能力，不是自动 Saga：系统不会自动判断外部副作用是否已完成，也不会自动执行补偿动作；但运行详情已经根据关联执行记录汇总 `REQUESTED / PARTIAL / COMPENSATED / FAILED` 状态。后续仍需补充外部系统适配器、补偿结果对原 Workflow 的自动收敛和人工对账闭环。
明确失败或驳回的补偿动作现在可以通过 `/ont/workflow/runs/{runId}/compensate/retry` 重试；`RECONCILIATION_REQUIRED` 仍必须人工确认后处理，避免重复副作用。

Workflow `inputSchema` 已接入运行时校验，启动和数据到达触发不会再仅凭“JSON 可解析”就放行非对象根输入、缺少必填字段、类型不匹配或数组元素不符合 Schema 的输入。

Workflow `outputSchema` 也已接入发布校验和结束节点校验；运行最终输出上下文不符合定义时会进入失败状态，不会误报为成功。

Workflow 运行记录已增加服务端分页、状态筛选和幂等键精确查询；原 `/ont/workflow/{id}/runs` 列表接口暂时保留用于兼容已有调用。

Workflow 已增加发布版本快照、历史版本查询和安全回滚；回滚只生成新的草稿版本，仍需经过校验和发布，不会直接改变当前线上版本。历史数据不会伪造快照，版本迁移部署后新发布版本开始留痕。

资产操作申请又补充了服务端数据隔离：普通用户只能查询、修改、提交、执行和删除自己创建的申请；平台管理员、空间管理员和运维人员才能查看全量并审批，避免仅凭页面权限操作其他用户的申请。Workflow 启动/续跑不再把外部动作执行包在管理库长事务中，运行状态按步骤落库，降低慢动作造成的长事务和锁风险。

质量任务日志查看接口已增加质量查询权限、日志根目录限制、文件名约束和 5 MB 大小上限，不再接受任意服务器文件路径。

## 二、已检查并修正的部署问题

补充功能修复：ETL 字段派生组件已补齐替换、表达式、哈希、正则提取和常量赋值五种此前返回空配置的类型；前端字段派生工作台现在可以配置这些类型，任务 JSON 会转换为受控 SQL 表达式。表达式禁止多语句分隔符和注释逃逸，并支持 `${字段名}` 占位符。

1. `deploy/start-all.sh --limit ... --check` 原先会无条件校验其它组件的配置，导致只检查 Redis 或 Nginx 也必须填写 DB-GPT、后端和数据库参数。现在按部署组分组校验。
2. `--check` 原先会在执行远程动作前创建 `deploy/.runtime/dolphinscheduler.token`。现在预检只在内存中使用临时值，真实部署时才创建 token 文件。
3. README 已按当前模块、Ant Design Vue、可选 ingestion 和实际启动依赖更新，并补充部署及本报告入口。

## 三、P0：上线前必须处理

### 0. 全局匿名白名单曾包含 `/**`（已修复）

`SecurityConfig` 原先把 `/**` 放入 `permitAll`，后面的 `anyRequest().authenticated()` 因此不会保护任何业务 URL；数据源、AI、接入和管理接口可能在未登录时被直接调用。本轮已删除该通配符，只保留登录、验证码、静态资源、明确的外部回调和调度器白名单。上线前仍需用未登录请求验证业务接口返回 401，并用已登录但无权限账号验证 403。

### 1. 配置仓库仍有明文密钥和默认口令

证据：

- `datamaster-server/src/main/resources/application.yml` 含模型 API key 默认值、固定 JWT secret、Knife4j 默认账号密码和通用密码策略。
- `application-dev.yml`、`application-prod.yml` 含数据库/外部数据源示例口令和固定 token。
- `deploy/deploy.yml` 默认使用 `postgres/postgres`、`datamaster/datamaster`，并把目标内网 IP 写入版本库。

风险：配置泄露后可直接访问数据库、调试接口、模型服务或伪造登录 token。

部署脚本现已增加生产配置硬校验：`deployment_environment` 默认按 `prod` 处理，PostgreSQL/Redis/DB-GPT/Neo4j/外部 ingestion 触发器和 DataMaster `jwt_secret` 的空值与常见弱口令会在远程动作前失败；开发环境必须显式设置 `deployment_environment=dev` 或 `allow_insecure_defaults=true`，且只输出脱敏 warning。SSH 命令日志也会隐藏数据库密码、模型 key、DS token 和触发密钥。应用基础配置已改为环境变量注入，生产部署模板关闭历史万能密码和 Knife4j basic/debug 能力；已经暴露过的旧 key 仍需轮换。

建议：删除真实或可用的默认 secret；全部改为必填环境变量/密钥文件；生产启动时继续对默认 JWT secret、Knife4j debug 开关做硬失败；轮换已经提交过的 key。

### 2. 离线 DolphinScheduler SQL 包含环境运行数据和旧地址

`deploy/packages/sql/dolphinscheduler.sql` 约 0.9 MB，包含大量任务实例、日志路径、旧 worker 地址和 `172.21.*:8080` 回调；`deploy/packages/sql/datamaster.sql` 约 8 MB。它们不是干净、可重复执行的结构/种子迁移。

风险：在新环境导入历史任务和实例；旧回调可能无法访问；重复初始化可能主键冲突或产生脏数据。

建议：拆分 schema、最小化种子数据和可选演示数据；所有回调使用部署模板变量；为初始化和升级脚本增加版本表、事务、幂等检查和回滚说明。

## 四、P1：高优先级工程缺陷

### 1. 部署脚本对非 root SSH 用户支持不完整（已修复上传路径问题）

原先 `deploy/start-all.sh` 使用 `scp` 直接把文件写入最终远程目录，只有目录创建和 chmod 使用 `sudo`。现在文件和目录先上传到 SSH 用户可写的 `/tmp/datamaster-deploy-*` 临时路径，再用 sudo `install/cp` 写入目标目录；非 root SSH 用户只需具备 sudo 非交互权限。当前默认开启 `deployment_backup_enabled`，覆盖前会在 `deployment_backup_dir` 保存文件或同文件系统硬链接目录快照，并保留最近版本；可用 `deploy/rollback.sh --restore` 恢复单个目标。

建议：继续增加整批部署事务级回滚和临时目录自动清理；现有单目标备份/回滚不覆盖数据库持久化数据，也不会自动重启服务。

### 2. 部署预检仍不是完整的离线包/远程能力检查（已补充远程预检和运行态健康检查）

`--check` 继续只验证本地配置、jar、SQL 和前端目录；新增 `--remote-check` 后可以通过 SSH 只读验证目标机 Docker、Java、systemd、磁盘空间、端口占用、目录权限和 sudo 非交互权限；新增 `--health-check` 后可以检查已部署容器、systemd 单元和服务端口是否处于运行状态，`--post-health-check` 可在部署完成后自动执行这套检查。它仍不能证明镜像 tag 与 tar 内部 tag 完全一致，也不会验证 DolphinScheduler/ChunJun/Flink 运行期业务健康或真实 Kafka/Doris 写入。

建议：继续补充离线 tar 内部镜像 tag、DolphinScheduler/ChunJun/Flink 版本矩阵和业务接口级健康检查；基础设施级运行态检查已通过 `--health-check` 落地，并支持部署后的 `--post-health-check` 自动等待服务就绪。

### 3. 依赖与文档存在漂移风险

历史文档仍描述 RabbitMQ 为平台运行依赖，但当前主部署没有 RabbitMQ 组件，ingestion 使用 Kafka/Doris 且默认关闭。专题文档中还存在迁移计划、实现记录和“已完成/待验证”混杂的状态。

建议：给文档增加“状态”和“适用版本”字段；每次模块/配置变更同步更新 README、deploy README 和专题文档；定期归档已失效方案。

## 五、P1：测试与可验证性不足

- 当前仓库可见 Java 测试类数量很少（盘点为 7 个），前端未发现 `spec/test` 测试文件。
- 没有 CI 配置来固定执行 Maven、前端 lint/build、部署脚本语法检查和 SQL 静态检查。
- 部署脚本虽然有 `--check`，但缺少无网络 fixture 测试，模板渲染、变量替换、limit 组合和 token 生命周期容易回归。

建议优先补充：权限边界、数据源路由、增量 ETL 幂等、AI Tool 审批、SQL 初始化幂等、部署脚本 shellcheck/Bats 测试，以及前端关键页面的最小 E2E 烟测。

## 六、P2：架构和运维改进项

- `spring-boot-starter-data-neo4j` 位于公共基础模块，导致可选血缘依赖在构建期扩散；可拆成独立 lineage 模块。
- 生产配置默认暴露 debug 日志、Swagger/Knife4j 调试能力和较大的上传限制（3 GB），需要按环境收紧。
- 单容器 `docker run` + systemd 方案缺少统一健康检查、滚动升级、备份、监控和告警约定。
- DataMaster 后端、DolphinScheduler、ChunJun/Flink、Kafka/Doris 的版本兼容矩阵没有作为发布物维护，升级时容易出现运行期不兼容。
- 部分血缘、AI、ingestion 流程仍采用静默降级或异步回写；平台数据智能体固定流程已返回 `PARTIAL` 和 `result.warnings`，但血缘、质量联动及其他异步编排仍需推广同一状态模型。

5. 再处理 Neo4j 依赖拆分、版本矩阵、健康检查和全链路可观测性。

## 八、业务功能完整性检查（重点）

以下问题不是部署问题，而是会直接影响业务结果、流程状态或用户对“功能已完成”的判断。

### P0：数据接入可靠性（已增加重试和死信）

原问题是 `IngestionKafkaConsumer` 使用 `ENABLE_AUTO_COMMIT=true`，可能在 Doris 写入完成前提交 offset。现在已改为关闭自动提交，并在单条业务处理成功后 `commitSync`；失败消息会保留 offset 并阻塞当前分区重试。配置死信 topic 后，持续失败的毒丸消息会在达到重试上限后转入死信并释放分区；未配置死信或死信发送失败时仍会阻塞，避免未经确认丢消息。

本轮增加 `max-retries`、`retry-backoff-ms`、`dead-letter-topic`、持久化重试次数和租约续期。超过重试次数后，配置了死信 topic 就转发并提交原消息 offset；未配置死信或死信发送失败时仍保留 offset，避免未经确认丢弃消息。现已提供按 topic/目标表筛选的死信查询、单条/批量人工重放和运行指标接口，且重放会恢复原 Kafka key 以保持分区路由语义；中断超过 10 分钟的 `REPLAYING` 记录可重新领取。

本轮又补充了主键配置和字段一致性校验：消息既没有 `key-columns` 也没有 `__keys` 时在进入 Doris 前直接拒绝；字段名按大小写不敏感匹配并规范化主键列，大小写重复字段会拒绝，避免日志键值、人工仲裁和实际 SQL 使用不同字段。Kafka 地址、消费组、租约/重试参数、Doris 数据源 ID 和冲突策略也会在消费者启动阶段校验，非法配置会明确停止消费而不是静默空转。

本轮补齐了运维暂停/恢复：`POST /ingestion/pause` 会在当前已拉取批次完成后暂停已分配分区，暂停期间仍持续 poll 维护 Kafka 心跳；`POST /ingestion/resume` 由同一个消费调度线程恢复分区，避免跨线程直接操作非线程安全的 `KafkaConsumer`。运行态新增 `PAUSING`、`PAUSED`、`RESUMING`，控制接口使用独立的 `ingestion:control` 权限并记录操作审计。

同时补充 Kafka 积压监控：运行态每 30 秒在消费线程内采样 `endOffsets - committedOffset`（没有提交位点时回退到当前 position），返回总积压和分区积压，避免只看“线程仍在运行”却不知道已经落后于生产端；采样失败只记录告警，不阻断业务消费。

### P0：Agent“取消”不是实际取消（本轮已修复基础状态竞态）

`PlatformAgentOperationService.cancel()` 只把数据库状态改为 `CANCELED`，流程实际通过多个 `CompletableFuture.runAsync()` 在后台执行；执行主流程没有统一的取消检查和 Future 中断。取消后后台任务仍可能继续创建数据源、探查任务、资产、本体和动作，最后把状态覆盖为成功或失败。

本轮已在每个主要阶段和状态持久化前检查取消标记，并用条件保护避免后台线程把 `CANCELED` 覆盖为运行中、失败或成功；元数据探查任务增加 Redis 取消标记，在数据库级边界停止后续处理。已经进入单次 JDBC 操作的外部任务不会被强行打断，取消接口会明确返回这一边界。

### P0：ingestion 写入曾是静默空操作（本轮已修复）

公共 `DbQuery` 接口中的 `addTableData()`、`updateTableData()` 在当前通用实现里返回 `0` 且不执行 SQL。ingestion 原先调用这两个方法并直接返回成功，导致 Kafka offset 已提交但 Doris 没有数据，属于静默丢写。

本轮已改为在 `DorisIngestionService` 内使用参数化 JDBC `INSERT`、`UPDATE` 和 `DELETE`，并对表名、列名做标识符清理，对业务值使用 `PreparedStatement`。仍需在真实 Doris Unique/Duplicate Key 表模型上验证更新返回值和并发行为。

### P1：ingestion CDC 删除语义（已补齐基础实现，仍需联调）

当前已支持消息中的 `__op`、`__operation` 或 `__eventType` 为 `DELETE`/`D`/`REMOVE`，按配置主键或消息 `__keys` 执行目标表删除；仍需与实际上游 CDC 消息格式、Doris 主键模型和重放流程联调。

如果项目只支持“新增/更新事件”，应在界面、配置和文档中明确限制；如果目标是 CDC 同步，则需要补齐 delete、墓碑记录和重放语义。

### P1：ingestion 冲突检查与写入不是原子操作

冲突策略 `INSERT`/`SKIP`/`ERROR` 仍需要先判断是否存在；本轮已将 `UPSERT` 写入改为 Doris 原生 `ON DUPLICATE KEY UPDATE`，把并发下的插入/更新交给数据库原子处理。冲突查询仍用于人工编辑仲裁，因此在人工编辑判断阶段仍存在额外读取窗口；实际表模型和 Doris 版本需要联调确认 `ON DUPLICATE KEY UPDATE` 支持情况。

建议优先使用 Doris 原生唯一键/事务语义，或把幂等键（topic、partition、offset/业务主键）落库并加唯一约束。

### P1：人工编辑仲裁缺少数据源和空间维度（已补齐新记录隔离）

`DorisIngestionService` 原先仅按 `targetTable` 拉取最近人工编辑记录，再按主键匹配，没有把空间 ID 纳入查询条件。同名表位于不同空间时，可能错误套用另一处人工编辑结果。本轮已按 `datasourceId + spaceId + targetTable` 查询，并兼容执行记录中逗号拼接的多目标表；消息含 `__spaceId` 时继续按空间过滤。

动作提交、数据到达失败留痕和回退记录现在都会固化 `datasourceId`，数据库迁移会为 `ONT_ACTION_EXECUTION.datasource_id` 建列和索引，并回填普通动作及可推导数据源的 FUNCTION 历史记录；COMPOSITE 关系步骤无法仅靠单字段安全推导，仍留空供人工核查。历史记录无法回填时，查询会兼容但无法完全消除旧数据的跨数据源误匹配风险；完成迁移并让新记录持续写入后，人工编辑仲裁按 `datasourceId + spaceId + table + primaryKey` 隔离。

### P1：智能体流程是“单数据源单活动流程”，并非真正多任务

Agent 流程现已按“用户 + 空间 + 数据源 + operationKey/conversationId/goal”生成稳定流程键；同一数据源可以并行运行多个不同目标，重试和续跑仍绑定原流程 ID。旧版按数据源生成的 flow_key 仍兼容读取，但新请求不会再无条件复用新流程。

### P2：部分功能失败时采用静默降级，用户难以判断是否完成（已补齐流程状态）

血缘关闭、资产未命中回退目录、人工编辑仲裁异常回退源数据等路径大量返回“可继续”的结果。业务上可能是合理降级，但当前页面和接口没有统一的 warning/degraded 状态，用户容易把“未执行、未授权、降级执行”误认为成功。

平台数据智能体流程现在会在核心接入完成、Skill 生成或 DB-GPT 能力同步失败时返回 `PARTIAL`，并把具体原因写入 `result.warnings` 和输出日志；固定流程页面会展示“部分完成/降级”状态。仍建议将同一状态模型推广到血缘、质量联动和其他异步编排接口。

### P1：外部副作用动作缺少统一执行边界（本轮已补齐 Webhook 动作）

此前动作执行链只有 SQL、函数和复合动作，Workflow 若直接扩展 HTTP 调用会绕过审批、幂等、审计和执行锁。本轮新增 `WEBHOOK` 动作类型：配置保存在动作版本快照的 `executionSteps` 中，复用现有提交/审批/Worker/执行记录链路；执行器统一限制协议、端口、目标解析地址、请求大小和重定向，模板解析失败按 fail-closed 处理。连接失败标记 `FAILED`，响应超时等无法确认外部系统是否已处理的情况标记 `RECONCILIATION_REQUIRED`，不自动重放；Workflow 的 `retryPolicy` 只有 `idempotent=true` 的 Webhook 才允许多次尝试。

仍需在真实外部接口上联调签名算法、对方幂等键约定和响应字段映射；生产部署应设置 `WEBHOOK_ALLOWED_HOSTS`，并把目标系统的幂等键/业务查询作为人工对账流程的一部分。
